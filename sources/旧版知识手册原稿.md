## 01 Java 集合：HashMap、ArrayList、ConcurrentHashMap

### 1.1 HashMap 的存储结构与 put/get

**JDK 8 HashMap** 由数组 `Node<K,V>[] table` 组成。数组的一个位置称为桶；桶内可以是单节点、链表或红黑树。哈希冲突指不同 key 最终落在同一桶，并不是 `hashCode()` 相同才算冲突。

定位桶的关键步骤：先取得 `key.hashCode()`，计算扰动后的哈希 `h = hashCode ^ (hashCode >>> 16)`，然后通过 `(n - 1) & h` 得到下标，其中 `n` 是长度为 2 的幂的数组容量。低位与高位混合，是因为数组下标主要用到哈希值低位。

`put(k,v)` 的主要流程是：桶为空则新建节点；如果首节点 key 相同则覆盖值；若桶已树化，走红黑树插入；否则沿链表找已有 key 或挂接新节点。当新增节点后达到链表树化阈值，会考虑树化；当元素总数超过 `threshold = capacity × loadFactor`，触发扩容。`get` 先定位桶、比较首节点，再根据桶类型沿链表或树检索。

**关键常量（JDK 8）：** 默认初始容量 16、默认负载因子 0.75；链表树化阈值为 8（添加节点后触发判断），退化阈值为 6；数组容量不足 64 时优先扩容，而不是树化。请注意“树化阈值 8”不等于任何时候桶中恰好有 8 个节点就立刻树化。

### 1.2 resize 为什么不用重新计算完整哈希

数组容量由 `oldCap` 扩为 `2 × oldCap`，对于某旧桶中的节点，只需要检查 `(e.hash & oldCap)`：

- 结果为 0：新下标仍是旧下标 `j`。
- 结果不为 0：新下标变成 `j + oldCap`。

原理是容量翻倍后，下标掩码仅多出一个最高有效二进制位。JDK 8 链表拆分为 `lo` 与 `hi` 两条链，保留原有顺序，避免 JDK 7 旧式头插迁移可能导致的链表顺序反转问题。**但“扩容时顺序保持”并不意味着 HashMap 在并发修改时安全。**

```java
int index = (n - 1) & hash;
// 当 oldCap = 16，新容量 = 32：
// (hash & 16) == 0  -> oldIndex
// (hash & 16) != 0  -> oldIndex + 16
```

**复杂度：** 普通情况下 `get/put` 期望 O(1)，大量碰撞下链表为 O(n)，树化后的桶查找为 O(log n)。不应将“HashMap 查询必定 O(1)”说成绝对结论。

### 1.3 equals 与 hashCode 的合同

两个对象如果 `equals` 为 true，`hashCode` **必须相同**；哈希相同却不要求对象相等。把可变字段作为 key 的 `hashCode/equals` 依据很危险：对象被放入 Map 后若字段改变，检索可能失败。

```java
final class UserKey {
    private final long id;
    UserKey(long id) { this.id = id; }
    @Override public boolean equals(Object obj) {
        return obj instanceof UserKey && ((UserKey) obj).id == id;
    }
    @Override public int hashCode() { return Long.hashCode(id); }
}
```

**典型追问：** HashMap 可以放 `null` key 吗？可以，JDK 8 中 `null` key 的哈希按 0 处理；但 ConcurrentHashMap 不允许 `null` key 或 value，避免并发场景中“没有映射”和“映射到 null”的语义混淆。

### 1.4 ArrayList 为什么扩容，以及删除的成本

`ArrayList` 底层是连续的 `Object[]`，按索引读取 O(1)；尾部追加在摊销意义下 O(1)，但扩容需要复制数组；中间插入/删除通常需移动后续元素，O(n)。JDK 8 中非空数组的一般扩容策略约为原容量的 1.5 倍，真实实现还要处理溢出、最小容量等边界。

`ArrayList` **不是线程安全容器**。`Collections.synchronizedList` 可加同步，但复合操作及迭代仍需正确加锁；读多写少的场景可考虑 `CopyOnWriteArrayList`，代价是写操作复制整个底层数组、写入和内存成本高。

### 1.5 ConcurrentHashMap 的并发策略

JDK 8 `ConcurrentHashMap` 不再采用 JDK 7 的 `Segment` 分段锁实现。数组初始化和空桶插入可使用 CAS；桶已有节点时，更新通常在桶首节点上进行 `synchronized` 同步；遇到树桶、扩容中的特殊节点有专门处理。扩容支持多个线程协助迁移。读取通常不加整个表的锁。

`size()` 在并发更新时更接近某一时刻的估计值，不适合用作严格同步条件。`putIfAbsent` 和 `computeIfAbsent` 可以实现“检查并插入”的原子语义；但映射函数不应执行很慢的远程调用或递归修改同一个 Map。

```java
ConcurrentHashMap<String, LongAdder> counters = new ConcurrentHashMap<>();
counters.computeIfAbsent("alarm", k -> new LongAdder()).increment();
long total = counters.get("alarm").sum();
```

**追问：** `ConcurrentHashMap` 是否绝对不会发生竞态？不是。它保证文档声明的单次并发操作语义，但 `if (!map.containsKey(k)) map.put(k,v)` 仍由两个独立操作组成，不是原子的。

### 1.6 红黑树与 TreeMap

红黑树属于自平衡二叉搜索树。常见规则：节点非红即黑；根为黑；红节点的孩子必须为黑；从一个节点到各个叶子空节点的路径黑节点数量相同。插入与删除通过**变色、左旋、右旋**维护平衡，因此搜索/插入/删除为 O(log n)。

左旋可以理解为：让节点 `p` 的右孩子 `r` 上升；`r.left` 变为 `p.right`；`p` 成为 `r.left`，同时修复父引用。旋转不会改变中序遍历顺序。`TreeMap` 依赖 key 的自然顺序或 Comparator 排序；比较结果为 0 的 key 会被视作同一个映射位置，因此比较器必须与预期键相等语义协调。

**面试口述：** “HashMap 倾向 O(1) 查找，TreeMap 提供 O(log n) 有序操作。红黑树不追求绝对平衡，而是控制高度，减少频繁调整。”

## 02 多线程：JMM、锁、CAS、AQS 与线程池

### 2.1 什么是 Java 内存模型（JMM）

JMM 不是物理内存布局图，而是定义线程间读写共享变量的可见性、顺序性和 `happens-before` 规则。编译器、CPU 可在不破坏单线程语义的前提下重排指令。多线程正确性不能只依赖“我在源码里先写 A 后写 B”。

`volatile` 对一个变量提供跨线程可见性，并禁止相关不安全重排序。对同一 `volatile` 变量的写与后续读可建立 `happens-before` 关系；但是 `count++` 属于读、加、写三步，**volatile 不保证复合自增原子性**。

```java
class Counter {
    private volatile int count;
    void wrongIncrement() { count++; } // 并发下会丢失更新
}
// 可替换为 AtomicInteger.incrementAndGet() 或加锁
```

### 2.2 synchronized 与 ReentrantLock 的区别

`synchronized` 基于 Java 监视器语义，退出同步块时（包括异常）自动释放锁，可修饰代码块或方法；`ReentrantLock` 是基于 AQS 的显式可重入锁，需在 `finally` 中 `unlock()`。后者提供 `tryLock()`、可中断锁获取、可选公平策略和多个 `Condition` 条件队列。

```java
lock.lock();
try {
    updateSharedState();
} finally {
    lock.unlock();
}
```

**常见误区：** `ReentrantLock` 一定比 `synchronized` 快、锁一旦竞争就会立即进入内核，都是不准确的。性能取决于 JDK 版本、竞争强度及临界区工作量。大多数普通业务同步优先选择更简单的 `synchronized` 或更高级的并发容器。

### 2.3 CAS 的价值与 ABA 问题

CAS（Compare And Swap）比较内存值与期望值，仅相等才写入新值，适用于竞争较低的无锁原子更新。并发竞争激烈时可能不断重试消耗 CPU。ABA 是指某个值由 A 改为 B 又改回 A，普通 CAS 只看当前值会误认为没变化；若业务关心“期间曾被修改”，可以采用版本号、`AtomicStampedReference` 等策略。

`LongAdder` 把高竞争计数分散到多个单元，降低热点争用，但 `sum()` 与并发更新之间不构成原子快照；不应把它当作需要强一致读的账户余额计数器。

### 2.4 AQS：state + 等待队列

AQS（AbstractQueuedSynchronizer）是同步器框架，核心包括一个 `state` 状态值、线程排队结构和获取/释放钩子。独占同步器（如 ReentrantLock）和共享同步器（如 CountDownLatch、Semaphore）在这个框架上定义不同状态语义。

线程获取失败时，可能进入等待队列并被挂起；锁释放后唤醒符合条件的后继节点尝试获取。**AQS 不是一种锁**，它是构建锁和同步器的基础设施。

### 2.5 线程池 ThreadPoolExecutor 的运行次序

构造参数包括：`corePoolSize`、`maximumPoolSize`、`keepAliveTime`、`TimeUnit`、`BlockingQueue`、`ThreadFactory`、`RejectedExecutionHandler`。

`execute(task)` 通常按以下顺序工作：工作线程少于核心线程数 → 创建核心线程；否则尝试进入任务队列；队列已满且工作线程少于最大线程数 → 创建非核心线程；再不行 → 执行拒绝策略。**使用无界 LinkedBlockingQueue 时，maximumPoolSize 往往不成为扩容上限的实际触发条件**，因为队列不容易满，风险反而是任务长期堆积和内存耗尽。

```java
ThreadPoolExecutor pool = new ThreadPoolExecutor(
    8, 16, 60, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(500),
    r -> { Thread t = new Thread(r, "alarm-worker"); t.setDaemon(false); return t; },
    new ThreadPoolExecutor.CallerRunsPolicy()
);
try {
    Future<?> future = pool.submit(this::processBatch);
    future.get(30, TimeUnit.SECONDS);
} finally {
    pool.shutdown();
}
```

`CallerRunsPolicy` 会让提交任务的线程执行任务，可形成背压，但如果提交线程是 Kafka poll 线程，执行过久可能使其无法及时 `poll()`，引发消费组重平衡。因此实际策略要联动队列容量、超时、暂停消费及任务耗时设计。

### 2.6 ThreadLocal、CompletableFuture 与常见事故

`ThreadLocal` 的值关联在每个线程维护的 `ThreadLocalMap` 中。key 对 ThreadLocal 是弱引用，value 仍可能强引用业务对象；线程池线程长期存活时，不恰当清理可能导致数据串用或内存滞留。建议使用 `try/finally` 调用 `remove()`。

`CompletableFuture` 适合组织异步依赖，但务必明确执行器、异常处理和超时；`join()` 抛出未检查的 CompletionException，`get()` 抛出受检异常；`allOf()` 本身只表示阶段完成，结果仍需逐个读取。不要大量异步任务默认使用公共 ForkJoinPool 来执行长时间阻塞 IO。

**经典面试题：**

- **为什么线程数不是越多越好？** 线程带来栈内存、切换和调度成本；吞吐瓶颈可能在数据库连接池或下游接口，增加线程反而恶化延迟。
- **如何排查死锁？** 结合 `jstack` / `jcmd Thread.print` 看线程等待关系、锁持有和调用栈，再定位反向获取锁的代码路径。
- **为什么一个线程池会 OOM？** 可能是无界队列堆积、任务持有大对象、线程数/栈消耗过大，或异步回调一直不释放引用；需要根据堆、线程和容器内存分别验证。

## 03 JVM：内存、GC、类加载与 OOM 排查

### 3.1 JVM 运行时数据区

线程私有的典型区域有程序计数器、Java 虚拟机栈、本地方法栈；线程共享的是堆和方法区的逻辑概念。HotSpot JDK 8 及后续用 **Metaspace** 实现类元数据存储（主要使用本地内存），不能把 Metaspace 直接等同于 Java 堆。`DirectByteBuffer` 等可使用堆外直接内存，线程栈、JIT、JNI、内存映射等也会占用进程内存。

`-Xmx` 只限制 Java 堆的最大值，不等于整个容器内进程占用上限。容器内存预算至少应包含堆、Metaspace、Direct Memory、线程栈、JVM 自身与本地库开销。

### 3.2 垃圾回收：可达性分析与分代

GC 根据 GC Roots 的可达性分析判断对象是否可回收。常见 Roots 包括线程栈中的引用、活动的类静态字段引用、JNI 全局引用等。堆分代思想利用“多数对象朝生夕死”的统计特征，减少扫描成本；但不同收集器实现细节不完全相同。

- **G1：** 将堆分成多个 Region，按停顿目标选择回收集合；在很多 JDK 版本中是默认收集器。关注 Young GC、Mixed GC、Humongous 对象、停顿时间和堆占用。
- **CMS：** 老一代低停顿收集器，已在后续 JDK 中移除。面试时区分当前 JDK，不要把 CMS 当成 JDK 17 可选的正常方案。
- **ZGC：** 面向低停顿场景，但适用条件和代际特性随 JDK 版本变化；不要只凭名称宣称“完全没有 STW”。

### 3.3 典型内存故障分类

**`java.lang.OutOfMemoryError: Java heap space`：** Java 堆对象分配失败。通常先查堆转储中的占用对象、引用链和分配热点，再判断是泄漏还是内存容量不足。

**`Metaspace` OOM：** 大量类或类加载器无法卸载、动态生成类过多，也可能是元空间上限偏小。

**`unable to create native thread`：** 系统/容器线程、内存或进程限制不足；不等于堆满。

**容器 `OOMKilled`：** 由操作系统或容器运行时因内存限制终止进程，可能根本没有 Java OOM 异常与 heap dump。只看 `-Xmx` 无法排除堆外问题。

### 3.4 可以实际执行的排查步骤

```bash
# 先确认 Java 进程和参数
jcmd <pid> VM.command_line
jcmd <pid> VM.flags
# 线程状态与堆概况
jcmd <pid> Thread.print
jcmd <pid> GC.heap_info
# 需要谨慎执行：堆转储可能引入明显 IO 与暂停开销
jcmd <pid> GC.heap_dump /path/heap.hprof
# Linux / 容器侧
cat /sys/fs/cgroup/memory.max       # cgroup v2
cat /sys/fs/cgroup/memory.current   # cgroup v2
```

生产建议配置 `-XX:+HeapDumpOnOutOfMemoryError` 和 `-XX:HeapDumpPath=...`，但必须预留磁盘空间、控制访问权限，避免转储文件泄漏敏感数据。JDK 8 与 JDK 17 的 GC 日志配置语法不同：JDK 17 通常使用 `-Xlog:gc*`；JDK 8 常用 `-XX:+PrintGCDetails` 等旧参数。

### 3.5 案例：Kafka 服务容器 8 GB、Xmx 7 GB 仍被杀

**分析路径：** 先确认是 JVM 抛 OOM 还是容器 `OOMKilled`；再检查 RSS / cgroup 内存、堆使用、线程数量、Direct Buffer、Metaspace，以及 Kafka 客户端缓冲和连接资源。`Xmx=7G` 在 8G 容器中只留约 1G 给全部非堆内存，具有明显风险，但不能仅凭配置就认定根因。

如果业务函数频繁创建 Kafka Consumer 或 Producer 且未关闭，还可能遗留网络线程、连接、缓冲等资源。修复时优先保证客户端复用或在生命周期结束时 `close()`；然后用持续压测和内存曲线验证是否消除了增长趋势。

**面试复述模板：** “先区分进程内 Java OOM 与容器级 OOMKilled；用 heap dump / GC 日志 / Native Memory Tracking 与容器指标交叉验证，定位到对象、线程或堆外内存，再做针对性修复与压测回归。”

## 04 Spring：IOC、AOP、事务、循环依赖

### 4.1 IOC 与 Bean 生命周期

IOC 意味着对象依赖由容器负责创建和装配；依赖注入只是实现 IOC 的常见手段。典型单例 Bean 创建过程中会经历：实例化 → 属性注入 → Aware 回调 → BeanPostProcessor 前处理 → 初始化方法 → BeanPostProcessor 后处理 → 对外可用。关闭容器时可触发销毁回调。

Spring Boot 自动配置通常利用条件注解、配置类与框架扩展点，根据 classpath、属性和现有 Bean 决定是否注册默认组件。“约定大于配置”不代表没有任何初始化逻辑。

### 4.2 AOP 代理的边界

Spring AOP 常见实现是 JDK 动态代理或 CGLIB 类代理。对于通过 Spring 代理对象调用的方法，切面才能有机会织入事务、日志等增强。**同一对象内部 `this.method()` 自调用通常绕过代理**，从而导致 `@Transactional`、`@Async` 等基于代理的能力不生效。

`private` 方法、`final` 方法等是否可被增强，与代理类型及具体机制有关。不要笼统地说“加了注解就必定产生事务”。

### 4.3 @Transactional 的真实语义

Spring 声明式事务通常由事务拦截器围绕方法调用完成：获取事务管理器 → 根据传播属性决定新建或加入事务 → 执行业务 → 提交或回滚。默认 `PROPAGATION_REQUIRED`；默认情况下运行时异常和 Error 会触发回滚，而检查型异常通常需显式配置 `rollbackFor`。

```java
@Service
public class OrderService {
    @Transactional(rollbackFor = Exception.class)
    public void createOrder(Order order) {
        orderMapper.insert(order);
        outboxMapper.insert(new OutboxEvent(order.getId(), "ORDER_CREATED"));
    }
}
```

这段示例用同一个数据库事务原子提交业务表与 Outbox 表记录，并不保证消息已经被 Kafka 消费。消息发送通常由独立投递器读取 Outbox 并重试，消费端还需幂等。

### 4.4 事务失效的典型原因

- 对象不是由 Spring 管理，或者通过 `this` 自调用。
- 异常被 `catch` 后吞掉，没有标记回滚。
- 抛出检查型异常但未配置相应回滚规则。
- 错误理解事务传播：`REQUIRES_NEW` 需要真正通过代理进入新事务边界。
- 多数据源、异步线程或跨服务调用没有自动共享一个本地事务。

**追问：** “给方法加 `@Transactional` 就可以让 ES 和 MySQL 一起回滚吗？”不可以。普通 Spring 本地数据库事务不包含 Elasticsearch 或 Kafka 这些异构系统，需要通过可靠事件、补偿、最终一致性等设计协调。

### 4.5 循环依赖、Bean 作用域与线程安全

Spring 经典单例 setter/field 注入循环依赖可在部分配置下通过提前暴露对象引用来处理，常被称为“三级缓存”思路；构造器循环依赖不能因此自动解决。Spring Boot 某些版本默认禁止循环引用，即使底层机制存在也不能当作推荐设计。

单例 Bean 默认不意味着业务代码线程安全：如果把请求状态写入 Controller 或 Service 的成员字段，就可能产生数据竞争。推荐无状态单例，将请求数据放在方法局部变量或明确管理的线程安全组件中。

## 05 MySQL / 关系数据库：B+ 树、索引、MVCC 和锁

### 5.1 为什么 InnoDB 使用 B+ 树作为主要索引结构

B+ 树是多路平衡搜索树。InnoDB 的 B+ 树中，非叶子节点主要保存索引键和页指针，叶子节点保存具体索引记录；叶子页之间有便于范围遍历的连接关系。与二叉树相比，一页中可以放更多分支，树高通常更低，更契合以数据页为基本单位的存储访问。

**聚簇索引与二级索引：** InnoDB 聚簇索引叶子记录包含整行数据；二级索引叶子通常保存二级索引列以及主键值。用二级索引找到主键后，如果查询列未被该索引覆盖，就可能再次查聚簇索引，即“回表”。

### 5.2 联合索引、最左前缀与覆盖索引

例如联合索引 `(tenant_id, status, create_time)` 按列次序排序。查询前两列等值并对第三列做范围过滤，通常可高效定位；只查询 `status`，不能直接依赖这个联合索引获得同样的前缀查找能力（具体计划仍由优化器决定）。

```sql
CREATE INDEX idx_alarm_tenant_status_time
ON alarm (tenant_id, status, create_time);

-- 能充分利用联合索引的前缀
SELECT id, create_time FROM alarm
WHERE tenant_id = 20 AND status = 1
  AND create_time >= '2026-11-01'
ORDER BY create_time LIMIT 20;

-- 无左侧 tenant_id 约束，是否使用索引应以 EXPLAIN 为准
SELECT * FROM alarm WHERE status = 1;
```

“索引遇到范围条件，后续列全部失效”是**过度简化**：范围条件常影响后续列能否继续用于缩小 B+ 树扫描范围，但后续列仍可能参与索引条件下推、覆盖或排序等，需结合具体 SQL、版本与 `EXPLAIN`。

### 5.3 回表、索引条件下推、排序

覆盖索引指查询所需的数据可直接从索引记录获取，从而省去部分回表。索引条件下推（ICP）允许在存储引擎读取索引记录时先过滤部分条件，减少无用回表。`ORDER BY` 能否利用索引取决于索引列顺序、等值/范围条件和排序方向等，不是“存在索引就不 filesort”。

索引并非越多越好：每次插入、更新、删除还需维护额外索引，同时占用磁盘和缓冲池。应根据真实查询与写入模式选择少量高价值索引。

### 5.4 MVCC、隔离级别与 Read View

InnoDB 的多版本并发控制依赖行版本信息、Undo Log 和可见性规则，使普通一致性读在许多情况下不需要阻塞写操作。Read View 决定一个事务能看到哪些版本。常见隔离级别包括 READ COMMITTED 和 REPEATABLE READ；两者在快照创建时机等方面存在差异。

**务必区分：** 普通 `SELECT` 的一致性读，与 `SELECT ... FOR UPDATE` / `UPDATE` 等当前读，看到的数据和加锁行为不同。MySQL InnoDB 默认 REPEATABLE READ 不能简单等同于“任何并发执行都不会出现幻读现象”；必须结合语句类型、锁与事务交错分析。

### 5.5 行锁、间隙锁、Next-Key Lock、死锁

InnoDB 常使用基于索引的记录锁；在特定隔离级别与访问路径下，会有间隙锁或 Next-Key Lock 用于控制范围插入。它并非一个“纯按行锁就不会锁范围”的系统。未命中合适索引的更新可能扫描并锁定更多记录，增大锁冲突风险。

死锁例子：事务 A 先锁订单 1 再等订单 2；事务 B 先锁订单 2 再等订单 1。数据库可能选择回滚其中一个事务。业务端应统一访问顺序、缩小事务、必要时有限次数重试，并记录死锁日志定位根因。

### 5.6 深分页与游标分页

```sql
-- offset 很大时可能扫描并跳过大量候选记录
SELECT * FROM alarm ORDER BY id LIMIT 1000000, 20;

-- 顺序扫描/游标翻页，不要求 id 连续
SELECT * FROM alarm WHERE id > 1000000 ORDER BY id LIMIT 20;
```

第二个 SQL **不要求 id 连续**：它寻找大于 1000000 的下一条实际存在的记录。如果排序键不是唯一值，应增加唯一的稳定排序字段，例如 `ORDER BY create_time, id`，并用 `(create_time, id)` 作为游标条件，避免同时间戳跨页重复/漏读。

### 5.7 如何用 EXPLAIN 做优化

先看是否扫表、索引候选和实际选择（`type`、`key`、`rows`、`Extra`）；再看过滤比例、是否回表、是否 filesort/temporary、是否产生过多行。`EXPLAIN ANALYZE` 的支持和语法与数据库版本有关。MySQL、OceanBase、PostgreSQL、Kingbase 的执行计划和索引实现不应完全混为一谈。

**常见问答：**

- **`LIKE '%abc'` 一定无法使用任何索引吗？** 通常无法用普通 B+ 树从左前缀做范围定位，但可能有其他索引或特殊访问路径；需要限定“普通前缀搜索”的语境。
- **为什么优化器不走我建的索引？** 可能统计信息、选择性、回表成本、排序代价、扫描行数等使全表扫描更便宜。
- **为什么 `COUNT(*)` 不一定慢？** 性能取决于引擎、条件、索引、缓存与执行计划，不能断言有固定 O(1) 结果。

## 06 项目实战：消息处理中心的架构、幂等和容量问题

### 6.1 一条告警从接入到查询的完整链路

一个典型链路是：外部生产者发布 Kafka 消息 → 消费者解析与校验 → 根据来源路由 → 计算业务幂等键 → 更新告警最新状态 → 将原始消息归档 → Elasticsearch 建索引与统计 → 查询服务/看板对外展示。每一步都有独立的失败方式：格式错误、重复消费、写入超时、索引不可用、消息积压、看板聚合变慢。

设计时不要只画组件方框，面试官会追问三个问题：**数据写在哪里、在哪个时点确认成功、失败后如何恢复。** 对同一条消息，写主状态表和历史明细往往承担不同目标：主状态按告警业务 ID 聚合去重，历史记录保留原始到达事件，不能随意以“历史表重复”为由删除。

### 6.2 告警合并和升级：写成可解释的业务规则

假设告警主记录由 `alarmId` 唯一标识，原始事件包含 `lastOccurTime`、`severity`、`source`。一种可解释的更新规则是：主记录不存在则创建；存在时更新 `lastOccurTime` 的最大值；当新级别高于既有级别时记录更高级别和其发生时间；满足业务定义的升级条件时重新打开已关闭告警。

该规则有多个并发陷阱：两个消费者同时读到旧级别；先到的消息事件时间反而更新；先写新记录后被旧记录覆盖。需要区分**到达顺序**、**事件发生时间**和**版本/序列号**。若同一告警必须有严格顺序，可以按 `alarmId` 作为 Kafka 消息 key，使同一个 key 在同一 topic 的分区内保持有序；但跨 topic 或发生重试、数据源时间不可靠时仍需在存储层保证正确的状态转移。

### 6.3 幂等性不是简单的“先查再插”

下面是有竞态的伪代码：`if (!exists(id)) insert(id)`。多个线程可以同时看到不存在，然后一起插入。更稳妥的办法是以**数据库唯一约束**、ES 固定 `_id`、原子 upsert 或版本校验作为最终仲裁，而不是依赖额外的查询。

```sql
-- MySQL 示例：由唯一键在数据库内判定冲突
CREATE TABLE processed_event (
  event_id VARCHAR(128) PRIMARY KEY,
  processed_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
-- 将事件处理标记与业务更新放入同一数据库事务，
-- 用唯一键冲突区分第一次处理与重复处理。
```

如果把 ES 当作主状态存储，固定 `_id` 的 `update` + upsert 只能保证对应文档按操作更新，不自动解决“旧事件覆盖新事件”的业务问题。脚本里需比较业务版本/时间，并确保规则能处理时间相同或乱序到达的边界；带有 `retry_on_conflict` 的重试也不能替代业务幂等判断。

### 6.4 Kafka 偏移量何时提交

消费者处理完一个批次的业务写入后，再提交已安全处理的 offset，通常实现 **at-least-once（至少一次）**。如果 ES 已写成功而 offset 尚未提交便崩溃，重启后该消息会再次出现，因此业务写入仍需要幂等。

反过来，先提交 offset 再进行 ES 写入，一旦写入失败，消费者可能再也不会拿到这段消息，产生丢失风险。若一个批次只有部分写入成功，不能直接提交整个批次末尾的 offset；要根据分区、成功的连续区间和重试策略推进可提交位置。

### 6.5 性能优化：先量化，再选手段

应对每个处理阶段监控：Kafka lag、poll 耗时、批次大小、解析失败率、ES 批量写入耗时与失败率、线程池队列长度、GC 暂停、Nginx upstream 延迟。**吞吐低不等于线程不够**：可能是慢 ES 查询、网络链路、单分区串行、下游连接池不足、过度同步或写入刷盘。

例如从日均 2 万增加到 4 万条原始消息，**日均**仅约 0.46 条/秒；真正决定容量的可能是分钟级峰值、单条处理时间、额外下游推送次数和历史积累，而不是只用日总量证明“高并发”。面试应准确说明峰值 QPS、P95/P99 耗时、积压恢复能力以及实际验证方式。

### 6.6 可直接回答的三个项目问题

**问：为什么主索引和历史索引分开？** 答：主索引用于告警当前状态聚合与快速检索；历史索引用于保留每次原始事件，二者写入频率、保留策略、查询维度不同。主索引必须定义去重和并发更新规则，历史索引更关注不可丢和可追溯。

**问：为什么线上出现 OOM？** 答：先描述症状（JVM OOM 还是容器 OOMKilled）和指标，再列证据（客户端生命周期、线程/缓冲增长、Xmx 与容器差距），最后讲修复与复现验证。不能只说“后来加大内存就好了”。

**问：ES 查询从几百毫秒变成几秒怎么办？** 答：先固定相同查询比较索引规模、分片数、缓存、CPU/IO、查询计划，再查是否深分页、脚本、高基数聚合、`text` 字段误用、跨大量日索引；做单变量调整和压测回归。

## 07 Redis：缓存、持久化、分布式锁和集群

### 7.1 常见数据结构与真实用途

Redis 的字符串可做缓存值、计数和简单状态；Hash 适合字段级对象数据；List 可用于简单列表/队列，但复杂可靠消息流更适合 Stream 或专门消息系统；Set 适合成员判重、交并差；Sorted Set 适合按分数排序、排行榜、定时任务索引。Redis 底层对对象采用不同编码，不能把外部数据类型直接等同于某一种固定底层结构。

缓存 key 设计建议包含业务前缀、版本与实体 ID，例如 `alarm:v2:detail:123`；过期时间与访问模式相匹配，避免无 TTL 的热点缓存长期积压。

### 7.2 缓存穿透、击穿和雪崩

- **穿透：** 反复查询不存在的数据，每次都绕过缓存击中数据库。可以短期缓存空结果、布隆过滤器和限流；布隆过滤器存在误判，不应直接替代权威数据库。
- **击穿：** 某个热点 key 到期，大量请求同时回源。可在单飞/互斥加载、逻辑过期与后台刷新之间选择，关键是限定等待和回源量。
- **雪崩：** 大量 key 在同一时间失效或 Redis 服务不可用，导致后端瞬间承压。可分散 TTL、分级降级、多副本和限流。

**缓存一致性：** Cache-Aside 通常写数据库后删除缓存，而不是幻想“数据库与 Redis 天然原子一致”。删除失败、并发旧值回填和消息延迟都需要通过重试、TTL、版本比较或事件通知降低不一致窗口。严格强一致业务不应只靠普通 Redis 缓存保证。

### 7.3 Redis 持久化与主从切换

RDB 是按时间点生成内存数据快照，恢复速度和文件紧凑性通常较好，但快照间数据可能丢失。AOF 记录写操作，可通过不同刷盘策略平衡安全性和性能；`appendfsync everysec` 常见但不等于“绝不丢一条”。具体部署还可能使用混合持久化。

主从复制通常是异步的；主节点刚确认写入，还没复制到从节点就发生故障切换，可能丢失已确认写入。Redis Cluster 提供分片与故障转移能力，但不是强一致数据库。

### 7.4 分布式锁：为什么 SETNX 还不够

一个基本加锁思路是 `SET key randomToken NX PX 30000`，使“仅在不存在时写入”和过期时间设置成为一个原子 Redis 命令。释放时必须比对 token 才能删除，避免客户端 A 锁过期后误删客户端 B 新获得的锁。

```lua
-- KEYS[1] 锁键，ARGV[1] 本客户端随机 token
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
```

**最重要的限制：** 如果 A 拿到锁后发生长时间 GC 暂停，锁过期，被 B 获取；A 醒来仍可能继续执行。对于不能容忍旧持有者写入的资源，需使用**fencing token（单调递增令牌）**并由下游资源拒绝旧令牌。普通 Redis 锁、自动续期和随机 token 均不等同于下游数据强一致保障。

### 7.5 Redis Cluster 的槽位与风险

Redis Cluster 使用 16384 个 hash slot，把 key 映射到槽，再由不同主节点负责槽位。涉及多个 key 的原子操作通常要求 key 位于同一槽，可以用 `{user:1}` 这样的 hash tag 控制槽位，但要谨防把热点全部集中到一个槽。

集群故障排查：先区分主节点不可用、网络分区、槽位迁移、复制延迟、客户端拓扑缓存过期；再看集群状态、节点日志与 key 分布。若主节点故障切换期间业务写不可用，不应只认为“Redis 有从节点所以必然零中断”。

## 08 Kafka：分区、副本、消费组和可靠性

### 8.1 分区与副本的本质

Topic 是逻辑消息流，Partition 是可并行读写的有序日志单位。单分区内消息按 offset 排列；**Kafka 不保证不同分区之间的全局顺序**。若相同告警必须按顺序处理，生产者可以用业务 key 做分区选择，但分区数变化可能改变后续消息分布；涉及顺序要求时要评估这一影响。

副本保证故障恢复：一个分区有 leader 和 follower，生产者通常向 leader 写入，follower 复制日志。ISR 是与 leader 保持足够同步的副本集合，其成员可能动态变化。副本因子 3 不意味着任何时刻都能承受 2 个节点故障且不丢数据，仍受 acks、min.insync.replicas、unclean leader election 与故障时机影响。

### 8.2 可靠生产的三个关键配置

`acks=all` 表示等到当前要求的 ISR 副本确认，而不是“所有配置副本即使掉线也必须确认”；`min.insync.replicas` 限制允许成功确认时所需同步副本数。开启 `enable.idempotence=true` 有助于避免同一生产者会话内由于重试产生的重复写入；适用的其他配置限制依 Kafka 客户端版本而异。

**重要边界：** Kafka 幂等生产者 ≠ 消费端只处理一次，也 ≠ 写入 ES 只发生一次。Kafka 事务与 `read_committed` 能协调 Kafka 内部的生产/消费处理，但端到端包括数据库或 ES 时仍需额外一致性设计。

### 8.3 消费组与分区分配

同一消费组内，一个分区在正常稳定状态下由组内一个消费者实例读取。消费者数超过分区数，部分消费者可能空闲。不同消费组可各自独立读取同一 Topic。

Rebalance 可能由成员加入/离开、心跳失联、超过 `max.poll.interval.ms`、分区变化等触发。重平衡期间如果 offset 未管理好，可能出现重复处理或较长暂停。消费循环不要被无限期的下游 IO 占满；可以采取暂停分区（pause）、异步处理加有界队列、限制每次 poll 大小等方式做背压。

### 8.4 offset 提交与重复消费

Kafka consumer 位置与已提交 offset 是两个不同概念：`poll` 已拉取消息，不代表业务已经成功写入。自动提交在某些场景下容易产生“处理失败但偏移量推进”的风险；手动提交后处理可获得至少一次语义，但可能重复消费。

```java
// 伪代码：实际需分区维度追踪连续成功 offset
while (running) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(500));
    for (ConsumerRecord<String, String> r : records) {
        validate(r.value());
        idempotentWrite(r.key(), r.value());
    }
    consumer.commitSync(); // 仅当当前批次全部成功时
}
```

此代码只演示顺序和思路。生产实现需要：分区级失败隔离、处理异常时禁止跳过失败消息、重试/死信策略、优雅停机、分区撤销回调以及保证 `poll()` 周期不超时。

### 8.5 消息积压如何定位

消费者 lag = 分区末端可读取位置与当前消费组已提交位置的差。应分别看每个分区，而不是只看总和。积压可能由消费慢、分区热点、消息突增、重复重试、ES 拒绝写入或消费者频繁重平衡引起。

改善顺序是：先找瓶颈；调整批处理、IO 并发和下游容量；确保分区数能支撑所需并行度；有界队列实施背压；最后验证峰值恢复速度。单纯增大 `max.poll.records` 可能放大单批处理时间，使 rebalance 更频繁。

### 8.6 Broker 与客户端版本、序列化

Kafka Broker 版本与客户端版本可以存在一定兼容范围，但升级前需检查协议兼容矩阵、默认行为、安全机制和配置变化。`StringSerializer` 输出 UTF-8 字符串字节；Java 原生 `ObjectOutputStream` 序列化的数据包含对象流头。用普通 JSON 字符串字节去喂 `ObjectInputStream` 反序列化器，常报 `invalid stream header`，**属于消息格式不匹配**，不是消费者组或网络端口故障。

生产上更推荐跨语言、可演进的 Schema（JSON Schema、Avro、Protobuf 等），配套版本兼容策略；Java 原生序列化存在兼容性、安全性和语言绑定问题，不宜作为长期跨系统协议。

### 8.7 Kafka 面试复述题

**问：如何保证消息不丢？** 答：分生产端（acks/副本/幂等/错误处理）、Broker（ISR/持久化/故障策略）、消费端（处理成功后提交 offset/重试/死信），并说明端到端无法只靠单一参数保证。

**问：为什么消息会重复？** 答：ES 写成功但 offset 未提交、生产者重试、rebalance 或故障恢复都可能造成重复，必须在业务数据写入处建立幂等。

**问：三个分区开 20 个工作线程就一定快吗？** 答：Kafka 分区读取并行度与组成员/分区数有关；消费者内部工作线程可并发处理消息，但必须保证同一业务 key 的顺序、背压和每分区 offset 正确提交，不能只以线程数估算吞吐。

## 09 Elasticsearch：倒排索引、分片、聚合与慢查询

### 9.1 倒排索引解决什么问题

传统扫描需要逐条检查文本，而倒排索引把“词项 → 包含该词项的文档”建立映射。`text` 字段一般经过分析器分词，适合全文检索；`keyword` 保留精确值，适合过滤、聚合、排序和精确匹配。错误地用 `term` 查询分词后的 `text` 字段，可能出现“明明存在内容却查不到”的问题。

```json
{
  "mappings": {
    "properties": {
      "alarmId": { "type": "keyword" },
      "severity": { "type": "integer" },
      "lastOccurTime": { "type": "date" },
      "message": { "type": "text" },
      "source": { "type": "keyword" }
    }
  }
}
```

**查询建议：** 不需要打分的精确条件放 `bool.filter`；需要相关性排序的全文查询放 `must` 或 `should`；尽量限制 `_source` 返回字段，避免返回超大文档。

### 9.2 分片、副本与写入刷新

索引由主分片与副本分片组成。分片数量会影响并行处理与分布能力，但更多分片也带来段、文件句柄、协调和管理成本。Elasticsearch 近实时检索：文档写入成功不代表立即被搜索可见，通常要经过 refresh；`refresh=wait_for` 可以等待刷新，但不应滥用为每次写入都强制 refresh。

按日建索引适合有时间维度的日志/告警类数据，易于过期删除和按时间范围筛选。但如果每天数据量太小，也可能造成大量小分片和查询开销；应根据保留时间、分片大小、查询范围与管理成本调整粒度，必要时评估 rollover/ILM。

### 9.3 aliases 与多来源路由

Alias 是一个或多个索引的逻辑名字，可降低业务对物理索引的直接耦合。别名同时指向多个索引时，写请求可能需要明确 `is_write_index` 指向唯一写入索引；读别名与写别名应按职责区分，避免历史索引误写或查询扫到不相关索引。

```json
POST /_aliases
{
  "actions": [
    {"add": {"index": "alarms-2026.11.07", "alias": "alarms-read"}},
    {"add": {"index": "alarms-2026.11.07", "alias": "alarms-write", "is_write_index": true}}
  ]
}
```

示例只展示 API 结构；实际按日索引切换需要在新增下一个写索引时，原子调整写别名，且确保同一写别名只有合适的写入目标。

### 9.4 深分页：from/size、search_after 与 PIT

`from + size` 很大时，参与查询的分片可能需保留和排序大量候选结果，导致 CPU、内存和延迟上升。`search_after` 通过上一页最后一条的排序值翻页；稳定翻页需要**确定性的排序字段和唯一打破平局的标识**。数据持续变化时可搭配 PIT（Point In Time）来维持一致视图，注意 PIT 的资源占用和超时。

```json
GET /alarms-read/_search
{
  "size": 20,
  "sort": [
    {"lastOccurTime": "desc"},
    {"alarmId": "asc"}
  ],
  "search_after": ["2026-11-07T10:00:00.000Z", "A-1001"],
  "query": {"range": {"lastOccurTime": {"gte": "now-7d"}}}
}
```

上例适用于排序组合在命中记录中唯一的情况；如果不同事件可能具有同样 `alarmId` 与时间，还需真正唯一的稳定排序键。`search_after` 适合顺序翻页，不适合低成本跳到第十万页。

### 9.5 去重、最新状态与聚合

若原始事件一条一文档，业务要每个 `alarmId` 只返回最新一条，可考虑在精确 ID 字段上使用 `collapse`，按事件时间倒序排序；或者先按 ID 聚合再取 top hits（取决于数据规模与返回目标）。若主索引本来已按 `_id=alarmId` 写成“每个告警一份当前状态”，应优先直接查询主索引，避免每次再做高成本去重。

```json
GET /alarms-read/_search
{
  "size": 20,
  "query": {"match_all": {}},
  "collapse": {"field": "alarmId"},
  "sort": [{"lastOccurTime": "desc"}]
}
```

**注意：** `collapse` 响应中的 `hits.total` 通常反映符合查询条件的文档数，并不是精确去重后的告警数。`cardinality` 可估计去重数量，但通常是近似值；需要精确计数时应另行设计索引或聚合方案。

`terms` 聚合用于分桶，适合可聚合的 `keyword` / 数值字段；高基数字段、大量 bucket 和跨多分片聚合可能明显占用内存。`composite` 聚合适合可分页遍历聚合桶，但与普通搜索结果分页不同。

### 9.6 慢查询和批量更新的实用技巧

慢查询先记录请求 JSON、命中索引/分片、耗时、返回 size、是否启用脚本/排序/聚合。再结合 slowlog、profile、hot threads、节点堆、GC 和磁盘 IO 分析。常见问题：通配符前缀搜索、不必要的 `wildcard`、无时间范围限制、跨大量索引、高基数聚合、脚本运算、深分页、字段映射不合理。

`_update_by_query` 适合按条件批量更新，但它按快照搜索并发起更新任务，可能遇到版本冲突；应理解 `conflicts=proceed`、`slices`、`requests_per_second`、异步任务查询等参数的影响。它不提供“所有文档同时原子修改”的语义，批量操作前先限定索引与过滤条件、备份或准备回滚策略。

**面试追问：** ES 为什么查询比 MySQL 快？答：对全文搜索、过滤与分布式分析等适配工作负载，倒排索引和分布式执行可能有优势；但精确主键点查、强事务更新或小规模关联查询，不应一概认定 ES 更快。

## 10 计算机网络：TCP、HTTP、HTTPS 和 Nginx

### 10.1 TCP 的三次握手

客户端发送 SYN 并携带初始序列号；服务端回复 SYN+ACK；客户端再发 ACK，双方建立连接。三次握手主要用于协商初始序列号、确认双向通信与连接状态，并不只是“因为三比二安全”。

TCP 在传输层提供有序字节流、重传、流量控制和拥塞控制，但不保证应用层每次 `read()` 恰好读到一个完整消息。粘包/拆包是应用消息边界设计问题，常见解决方式是长度字段、分隔符或固定长度协议。

### 10.2 TCP 的四次挥手与 TIME_WAIT

TCP 连接两个方向可以分别关闭，因此常见释放流程包含双方各自的 FIN 与 ACK，某些报文可能合并。主动关闭方常进入 TIME_WAIT，目的包括确保最后 ACK 可在需要时重传以及避免旧连接报文干扰新连接。不能看到大量 TIME_WAIT 就直接判定“系统有严重泄漏”；需要结合短连接频率和端口资源判断。

### 10.3 HTTP/1.1、HTTP/2 与 HTTPS

HTTP/1.1 支持持久连接，但请求在同一连接上的并发与队头阻塞有约束；HTTP/2 引入多路复用、头部压缩等机制，但底层 TCP 丢包仍可能导致传输层队头阻塞。HTTP/3 基于 QUIC/UDP，在连接迁移和丢包隔离方面具有不同特性。

HTTPS 通常是 HTTP 运行在 TLS 保护的连接上。TLS 通过证书校验服务器身份、密钥协商建立对称加密会话，保证传输的机密性和完整性；不是“用服务器公钥加密所有 HTTP 正文”。

### 10.4 Nginx 反向代理中的耗时从哪里来

请求链路可分为：客户端建连 → Nginx 排队/处理 → 建立或复用 upstream 连接 → 后端业务处理 → 响应返回。分析时对照 access log 中的请求总时长与 upstream 响应耗时，结合后端线程池、数据库、日志写入与连接池指标。

```nginx
upstream app_backend {
    server 10.0.0.10:8080;
    keepalive 64;
}
server {
    listen 80;
    location /api/ {
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_connect_timeout 3s;
        proxy_read_timeout 30s;
        proxy_pass http://app_backend;
    }
}
```

示例只是展示 upstream keepalive 的配套要点。连接池复用是否有效，还受后端 keep-alive、连接上限、上游应用协议和部署模式影响。Nginx 的 `worker_connections`、文件描述符限制及网络 backlog 需协同评估，不能只改一个参数就保证吞吐暴涨。

### 10.5 压测指标必须同时看吞吐和延迟

QPS 表示每秒处理的请求数；P95/P99 反映尾部延迟。压测时固定并发、数据规模、缓存预热、机器资源、响应体大小、成功率，并检查 JMeter 自身 CPU/网络是否成为瓶颈。**吞吐上升但错误率激增、尾延迟失控不是成功优化。**

**问：直连后端比走 Nginx 快很多，怎么排？** 答：确保压测请求完全一致；对照 access log/upstream 耗时、keepalive、连接复用、TLS/日志开销、worker 与 fd 限额，再核查是否是后端在不同压测模式下受到连接和并发差异影响。

## 11 分布式系统：幂等、限流、重试、熔断和一致性

### 11.1 分布式调用的五种不确定性

一次请求发出后，调用方可能遇到：目标根本未收到、目标收到但失败、目标处理成功但响应丢失、目标处理缓慢、调用方自己超时。**超时并不等于失败**：当调用方不知道下游是否已提交时，直接重试可能造成重复扣款或重复写入。

因此设计分布式接口时，要同时有：幂等键、超时预算、有限重试、可观测性，以及无法自动判断状态时的查询/对账接口。

### 11.2 幂等的实现方式及适用范围

幂等指同一业务操作执行多次，外部可观察结果与执行一次相同。`GET` 语义通常可设计为幂等，但单纯按 HTTP 方法判定是否幂等不可靠，仍需考虑实际副作用。

常见实现：客户端传 `requestId`；后端将其作为唯一键建立处理记录；使用事务把处理记录与业务状态一起写入；后续相同请求返回首次处理结果或可查询状态。不能“第一次处理开始”就返回成功，若事务还未提交应将处理中状态和重复请求的行为定义清楚。

**需要区分：** “数据不重复插入”和“业务操作幂等”不同。例如同一条订单通知重复执行一次扣库存，即使通知日志没有重复行也仍可能扣两次库存。

### 11.3 限流、熔断和降级各解决什么问题

- **限流**限制进入系统的请求速率或并发数，防止系统超载；令牌桶允许一定突发，漏桶倾向平滑处理速率，信号量限制同时在途的请求数。
- **熔断**在依赖故障频繁时暂时停止继续请求该依赖，用状态机减少级联故障；通常具有关闭、打开、半开等状态。
- **降级**是主动以部分功能/较弱结果换取核心路径可用，例如看板暂用缓存数据，但不能对资金操作随意返回“成功”。

```java
// 示意：无论流量多高，都限制同时向慢 ES 发出的请求数
Semaphore slots = new Semaphore(20);
if (!slots.tryAcquire(50, TimeUnit.MILLISECONDS)) {
    throw new RejectedExecutionException("downstream busy");
}
try {
    queryElasticsearch();
} finally {
    slots.release();
}
```

### 11.4 重试必须有条件、上限和退避

适合重试的是暂时性网络失败、可恢复的服务忙碌、明确幂等的操作。**参数错误、权限失败、确定性的业务约束错误**不应无脑重试。推荐指数退避加随机抖动（jitter），避免大量客户端同一时间再次冲击故障服务。

还要限制整个请求链路的截止时间。若上游超时 3 秒，下游每次超时 5 秒再重试 3 次，配置本身已经不自洽。任务型后台流程可将重试转移到队列，而不是让用户请求长期阻塞。

### 11.5 分布式事务：本地事务与最终一致性

跨数据库、消息队列、ES 的更新通常无法依赖一个简单的 `@Transactional` 统一回滚。常见方法包括：

- **Transactional Outbox：** 业务表和待发送事件表在一个数据库事务内提交；投递器可靠重试；消费者幂等。
- **Saga：** 将长流程拆成可独立提交的局部事务，并定义补偿动作。补偿不是数据库回滚，可能失败且需要重试。
- **TCC：** Try 预留、Confirm 确认、Cancel 释放，对资源操作有较强侵入性。

架构决策要基于允许的不一致窗口、故障成本、系统数量和业务复杂度。不要见到跨服务就机械引入分布式事务框架。

### 11.6 CAP、可用性与一致性不要混淆

CAP 关注发生网络分区时，一致性与可用性的取舍；它不是所有系统日常只能三选二的性能标语。“最终一致”也不代表数据最后一定自动对齐：必须有可靠重试、冲突处理、异常补偿与对账机制。

**面试题：如何实现订单创建后异步通知？** 使用数据库事务落地订单与 outbox 事件；投递器发送 Kafka 成功后标记事件；消费者使用事件 ID 幂等落库；配置重试、死信、告警和定期对账；并说明发送成功与下游业务完成不是一回事。

## 12 算法与数据结构：理解复杂度并能写对代码

### 12.1 时间复杂度到底在比较什么

大 O 描述输入规模增长时某个算法资源消耗的增长上界。`O(log n)` 表示输入翻倍时，工作量通常只增加一个近似固定的步骤数；对于二分，`n=1024` 最多约 10 次折半即可缩小到一个位置。底数为常数时不影响大 O 记号。

常见操作：数组按下标访问 O(1)；无序链表查找 O(n)；平衡二叉搜索树查找 O(log n)；归并排序 O(n log n) 时间、一般需 O(n) 额外空间；散列表平均查找期望 O(1)，退化情况由具体实现决定。

### 12.2 二分查找：最容易错的是边界

对于有序数组查找第一个 `>= target` 的位置，可使用左闭右开 `[left, right)`。无论是否找到完全相等的值，返回的 `left` 都是插入位置。

```java
static int lowerBound(int[] a, int target) {
    int left = 0, right = a.length;
    while (left < right) {
        int mid = left + (right - left) / 2;
        if (a[mid] < target) left = mid + 1;
        else right = mid;
    }
    return left;
}
```

例如 `[1,3,3,7]` 查找 3 返回下标 1；查找 4 返回下标 3。写题时应说明循环不变量：“答案始终在 `[left,right)` 范围内”。

### 12.3 链表、二叉树、堆与 DFS/BFS

**链表：** 插入删除已定位节点可 O(1)，但找到目标通常 O(n)。快慢指针可找中点、检测环；反转链表需维护 `prev`、`curr`、`next` 三个引用，避免丢链。

**二叉树：** 前序根左右、中序左根右、后序左右根；BST 的中序遍历有序（具体是否允许重复键取决于实现）。树若不平衡，普通 BST 查找可能退化 O(n)。

**堆：** 常用数组实现的完全二叉树，最小堆根为最小元素，插入/取出堆顶 O(log n)，读堆顶 O(1)。适合 Top K、任务优先级、合并多个有序流。

**DFS/BFS：** DFS 可用递归或显式栈，BFS 使用队列按层扩展。在无权图求最少边数路径，BFS 通常更自然；有权图不一定适用普通 BFS。需要 `visited` 防止图中环无限重复。

### 12.4 红黑树与 B+ 树的比较

| 对比项 | 红黑树 | B+ 树 |
|---|---|---|
| 分支数量 | 每个节点最多 2 个孩子 | 每个内部节点可有多个孩子 |
| 平衡要求 | 通过颜色约束高度 | 叶子通常位于同一层 |
| 典型目标 | 内存中有序 Map、Set | 数据库/存储索引 |
| 查找复杂度 | O(log n) | O(log_m n)，m 是分支因子 |
| 范围扫描 | 中序遍历 | 叶子节点顺序连接通常更合适 |

这里的“数据库用 B+ 树”也不是所有数据库和所有索引的通用规则；例如 PostgreSQL 常用 B-tree，也有 Hash、GIN、GiST、BRIN 等不同索引类型，且具体内部组织与 InnoDB 存在差异。

### 12.5 面试手写：两数之和

```java
static int[] twoSum(int[] nums, int target) {
    Map<Integer, Integer> seen = new HashMap<>();
    for (int i = 0; i < nums.length; i++) {
        int need = target - nums[i];
        if (seen.containsKey(need)) {
            return new int[]{seen.get(need), i};
        }
        seen.put(nums[i], i);
    }
    return new int[0];
}
```

解释：HashMap 保存先前数字到下标的映射，单次遍历 O(n) 期望时间、O(n) 额外空间。先查后放能避免同一个元素重复使用。若目标与元素可能溢出 `int`，应调整数值类型或约束。

### 12.6 面试手写：LRU 缓存

LRU 需要 O(1) 查询、O(1) 移动最近访问节点、O(1) 淘汰最久未访问节点。通常使用 HashMap + 双向链表；Java 可以直接通过 `LinkedHashMap` 的 access-order 实现。

```java
class LruCache<K, V> extends LinkedHashMap<K, V> {
    private final int capacity;
    LruCache(int capacity) {
        super(16, 0.75f, true); // true: 按访问顺序
        if (capacity <= 0) throw new IllegalArgumentException();
        this.capacity = capacity;
    }
    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > capacity;
    }
}
```

这段实现**不是线程安全的**；如果多个线程共享实例，需增加同步策略。生产缓存还应考虑 TTL、容量估算、统计和淘汰策略，不能把面试题代码直接当成高并发缓存组件。

## 13 AI / Agent 后端：RAG、Embedding、Tool Calling、MCP

### 13.1 LLM 应用后端的真实职责

模型服务平台不只是“HTTP 请求转发到一个大模型”。通常还要处理鉴权、模型路由、限流、Token 配额、上下文管理、异步/流式响应、超时重试、费用统计、工具授权、日志脱敏和故障降级。

关键服务指标包括首 Token 延迟（TTFT）、输出速度（tokens/s）、端到端耗时、并发会话数、错误率和每次请求 Token 成本。长上下文通常影响 Prefill 开销；解码阶段会反复访问注意力缓存（KV cache），显存和并发容量密切相关。

### 13.2 什么是 Embedding 与向量检索

Embedding 将文本等内容映射为数值向量，使语义相近的文本在向量空间中更靠近。相似度可采用余弦、内积或 L2 距离；选择何种指标要与模型训练方式和向量是否归一化对应。

向量检索常使用 ANN（近似最近邻），例如 HNSW 图结构，用更低检索延迟换取一定的近似误差及索引构建/内存开销。**相似度高不等于事实正确**：它只表明向量空间相近，不能替代权限校验、时间有效性判断或准确答案验证。

### 13.3 RAG 端到端链路

典型 RAG 系统由：文档读取 → 清洗/结构识别 → 分块 → Embedding → 向量与元数据存储 → 检索 → 重排 → 生成 → 引用与评价构成。

对于复杂 PDF 或表格，直接按固定字符数切分容易把标题、列关系和上下文拆散。可以先做版面结构识别，再按标题/段落语义切块；分块太大增加噪声与成本，太小则丢语境。常见改善是“召回小块，回答时扩展父块”，或加入基于关键词的检索。

**混合检索：** BM25 等稀疏关键词检索擅长准确关键词、代码、编号；向量检索擅长语义近似。可将两种结果融合（如 RRF），再按业务权限和时间过滤，必要时使用 reranker 排序。

### 13.4 结合 PostgreSQL / pgvector 的设计

向量表常包含：`document_id`、`chunk_id`、`content`、`embedding`、`source`、`updated_at`、`tenant_id`。如用 1024 维向量，则字段维度必须与嵌入模型输出一致；不要把另一模型生成的不同维度/空间向量直接混用。

```sql
-- pgvector 示例，扩展已安装；参数需按模型维度调整
CREATE TABLE doc_chunk (
  id BIGSERIAL PRIMARY KEY,
  document_id BIGINT NOT NULL,
  tenant_id BIGINT NOT NULL,
  content TEXT NOT NULL,
  embedding vector(1024) NOT NULL
);
CREATE INDEX idx_doc_chunk_embedding
ON doc_chunk USING hnsw (embedding vector_cosine_ops);

-- 余弦距离运算符 <=>；越小表示越相似
SELECT id, content
FROM doc_chunk
WHERE tenant_id = 1
ORDER BY embedding <=> '[0.1,0.2,...]'::vector
LIMIT 5;
```

上例的 `'[0.1,0.2,...]'` 是占位符，不能直接作为真实 1024 维向量执行。生产环境应使用参数化 SQL，先做租户/权限过滤，并用真实数据评估过滤选择率与 ANN 召回率。注意高选择性过滤与 ANN 查询可能存在检索策略上的取舍。

### 13.5 Tool Calling 和 Agent 的差别

Tool Calling 指模型根据输入选择工具及生成结构化参数，由宿主应用**验证参数、检查权限并实际调用工具**，再将工具结果作为上下文返回模型。模型并不应该直接获得无限制的系统权限。

Agent 在工具调用基础上加入目标拆解、循环决策、状态持久化、失败恢复及人工审批。一个可靠的执行循环需要设置最大步数、成本预算、调用超时、工具白名单，并记录每一步输入输出以便审计。

```text
用户请求
  ↓
意图识别 / 身份与授权
  ↓
模型选择工具 + JSON 参数
  ↓
Schema 校验 + 权限校验 + 人工审批（高风险操作）
  ↓
执行工具 → 结果结构化 → 模型生成答复
```

### 13.6 MCP：Host、Client、Server 的边界

MCP（Model Context Protocol）是一种用于让 AI 应用和外部工具/资源交互的标准化协议。常见角色为：Host（承载 AI 应用）、Client（建立协议连接）、Server（暴露工具、资源等能力）。它并不是“所有模型请求都必须经过 MCP”，也不自动解决鉴权、权限最小化和多租户隔离。

面试时最容易加分的细节：工具参数采用明确 schema；高风险写操作必须经过身份与权限检查；对工具返回内容视为不可信数据；防止提示词注入诱导越权调用；记录审计与执行结果。

### 13.7 RAG / Agent 的质量评估

不能只挑几个问题觉得回答“挺像样”。建议构造带标准答案与证据位置的评价集，按问题类型统计：检索召回率、Top-K 命中率、回答正确性、引用准确度、拒答质量、P95 延迟和单次费用。线上还需要观察错误工具调用率、超限率与任务完成率。

**面试追问：**

- **为什么向量搜索找不到精确编号？** 纯语义向量对精确字符可能不敏感；增加 BM25/关键词检索、字段过滤和混合排序。
- **为什么找到对的资料仍然答错？** 可能是上下文截断、证据冲突、提示词约束弱或生成幻觉；需加引用、重排、结构化证据和评测。
- **如何防止 Agent 自动删除数据？** 只暴露最小权限工具；写操作加入审批、幂等与预演；用授权校验、审计日志和回滚/补偿限制损害。

## 14 面试综合实战问答：把知识串成完整答案

### 14.1 线上 CPU 突然 100%，你怎么处理？

先判断是整机还是某个容器、单核还是多核、流量是否同时变化。用 `top -H -p <pid>` 确认高 CPU 的线程 TID，将十进制线程号转十六进制后在 `jstack` 中查对应 `nid`；结合方法栈、GC、线程池、死循环/自旋判断。若是 GC 高占用，先查对象分配和堆压力而不是盲目调大线程池。最后通过回滚、限流或修复恢复服务，并对比故障前后指标。

### 14.2 接口超时，但数据库 SQL 很快，问题在哪？

按总时延拆分：网关排队和 upstream 连接、认证过滤器、业务线程池等待、缓存/远程服务调用、序列化、日志同步写入、数据库连接池等待。**SQL 执行快不代表拿到数据库连接也快**。需要 trace/span 和各阶段计时，而不能只看方法内某条 SQL 的耗时。

### 14.3 一个接口突然返回大量重复数据，怎么定位？

检查源端是否重复发送、Kafka 是否发生重平衡与重试、消费者 offset 提交时机、业务幂等键是否稳定、写入库是否有唯一约束；再检查 ES 查询是否同时扫描主索引和历史索引、Alias 是否包含重复数据、业务层分页去重是否仅在单页内生效。先定义“重复”到底是事件重复还是同一告警的多次历史记录。

### 14.4 为什么服务重启能暂时解决内存问题？

重启清除了进程中的对象、线程和连接，可能临时缓解泄漏或缓存过度增长，但不能证明根因已消除。要记录重启后内存随时间增长曲线，结合对象直方图、堆转储、线程数、直接内存与连接数确认增长源头。若在稳定流量下持续单调增长，就更有理由怀疑资源泄漏或无界累计。

### 14.5 为什么有索引的 SQL 依旧很慢？

索引可能选择性低、扫描命中行仍很多、需要回表、排序不能使用索引、存在锁等待、分页 offset 大、统计信息不准确或缓存/IO 受限。先用执行计划和实际耗时定位，不应该只靠“有索引”下结论。

### 14.6 如何评估 Kafka 需要多少分区？

先测得单分区在当前生产者、消费者处理方式和下游条件下的实际吞吐及尾延迟，再结合峰值、容错与未来增长预留容量。注意副本因子、Broker 资源、分区过多的元数据/文件句柄成本，以及需要同 key 有序处理的需求。增加分区后已有 key 的后续映射可能变化，必须评估顺序边界。

### 14.7 如何设计可靠的告警“关闭”接口？

明确关闭业务权限、告警当前状态和允许转换的状态；使用唯一 ID 与版本条件执行更新，避免关闭动作覆盖更新的高优先级告警；返回是否真正发生状态变化而不是只返回 HTTP 200。对外重复请求保证幂等，对数据库和 ES 的跨存储同步使用可补偿事件；保留操作者、时间、原状态和理由等审计记录。

### 14.8 ES `_update_by_query` 在生产环境有什么风险？

一次命中范围误写可能改动大量文档；任务期间可能发生版本冲突，跨分片更新不具备整体事务；大规模写入会引起磁盘、CPU、segment merge 和查询延迟上升。执行前先跑 `_search` 验证过滤条件、检查样本、准备快照/恢复方案，合理限制批次与速度，并记录异步 task 状态和失败数。

### 14.9 为什么不把所有事情都做成异步？

异步提高并发组织能力，却会引入任务队列、积压、顺序、背压、取消、异常处理、状态一致性和可观测性成本。如果业务必须立即确认结果，异步也不能凭空缩短下游处理时间。先确定链路 SLA、服务瓶颈和可接受的一致性窗口，再决定采用同步、线程池、消息队列还是批处理。

### 14.10 你的项目最值得讲的技术亮点是什么？

围绕一个真实问题用“背景 → 约束 → 诊断证据 → 解决方案 → 结果与代价”的顺序回答。例如：消息中心发生周期性容器 OOMKilled；先区分 heap OOM 与容器内存超限，再检查消费者生命周期、线程与堆外缓冲及 Xmx；修复资源释放并调整内存预算；最后说明压测观察周期、内存曲线和错误率是否回归。**没有做过的测量不要编造成事实，结果可以如实表述为“问题已缓解，仍在持续观察”。**

## 附录 A：面试中最容易说错的 20 个结论

1. `volatile` 保证可见性和相关有序性，但 `i++` 不因此原子。
2. HashMap 链表长度达到某个值，不一定马上树化，还受容量和实现逻辑影响。
3. HashMap 扩容迁移高低链表的机制，不能用来证明它线程安全。
4. ConcurrentHashMap 的单次原子 API，不会让任意多个 API 的组合自动原子。
5. Java 堆上限不等于 Docker 容器中 JVM 进程的内存上限。
6. 容器 OOMKilled 不一定伴随 `OutOfMemoryError` 或 heap dump。
7. ThreadLocal 的弱 key 不等于值一定立刻被回收；线程池任务用后应移除。
8. 线程池最大线程数不是一到高负载就立刻创建到上限。
9. `@Transactional` 内部自调用通常不会经过 Spring 事务代理。
10. Spring 本地事务不能自动使 Kafka、ES 的写入一起回滚。
11. `id > N ORDER BY id LIMIT K` 不要求 id 连续。
12. 联合索引的“最左匹配”不能简化成“范围后的列完全没用”。
13. MySQL 的索引是否被选择取决于优化器成本，不是有索引就必走。
14. Redis 主从异步复制不保证故障切换时零数据丢失。
15. Redis 锁的 TTL、续期和删除 token 校验，不自动提供 fencing 保证。
16. Kafka 分区内有序不等于跨分区全局有序。
17. Kafka 生产者幂等不等于消费者业务端恰好处理一次。
18. ES `collapse` 的 `hits.total` 不能直接当精确去重计数。
19. HTTP 超时不证明下游业务没有完成，盲目重试会造成重复副作用。
20. RAG 召回相似文档不等于答案已经得到事实验证。
