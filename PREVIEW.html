多线程与 JMM · 第 2 节

volatile 可见性与原子性：为什么两个线程各加一，结果却是 1？

上一节我们知道：A 先写 data 再发布 volatile ready，B 先获取 ready 再读 data，就能建立可见性保证。可是有人问：既然 volatile 能让其他线程看到最新值，为什么两个线程做 count++ 还是可能少加一次？

30 秒速懂

把 count++ 想成两个人在一张纸上登记人数。两个人都想让人数加一：

  1. A 看纸：当前 0；B 也看纸：当前 0。
  2. A 心算 0 + 1 = 1；B 也心算 0 + 1 = 1。
  3. A 写回 1；B 再写回 1。

两个人都认真执行了“加一”，结果却只有 1，丢失了一次更新。

volatile 让读写共享变量遵守特定的可见性与顺序规则，但不会把“读 → 加 → 写”包成一个别人不能插队的整体。要保证这一整个操作不被并发破坏，可使用 AtomicInteger.incrementAndGet() 或同一把锁保护的 synchronized。

1. 反例：volatile 已经加了，为什么还是有错？

class Counter {
    volatile int count = 0;

    void addOne() {
        count++;  // 看着只有一行，其实不是一次不可分割的更新
    }
}

// 线程 A：counter.addOne();
// 线程 B：counter.addOne();

直觉是：初始为 0，A 加 1，B 再加 1，最后 2。

但在并发场景里，A 和 B 不一定“一个完整做完，再轮到另一个完整做”。count++ 从逻辑上至少有三个步骤：

int oldValue = count;   // 第一步：读共享值
int newValue = oldValue + 1; // 第二步：在自己的计算中加一
count = newValue;       // 第三步：写回共享值
先看清“原子性”是什么意思

原子操作：在我们讨论的并发意义下，这个操作作为一个不可分割的整体完成；别人不能在中间插入一次竞争性的更新，导致这次操作的效果丢失。

volatile int count 的单次读、单次写有相应的原子性与可见性保证。但 count++ 是一个复合的“读—改—写”，单步安全不代表组合起来安全。

2. 动手看动画：两次 ++ 是怎么变成一次的？

先选择 「volatile count++」，连续点“下一步”，尤其注意：A 读到 0 后、写回之前，B 也可以读到 0。接着切换到 AtomicInteger 和 synchronized，观察为什么最终都能得到 2。

2.1 把第一条动画翻译成时间线

共享变量 count = 0

时间↓       线程 A                       线程 B
----------------------------------------------------
  ①        读取 count → 0
  ②                                     读取 count → 0
  ③        计算 0 + 1 → 1
  ④                                     计算 0 + 1 → 1
  ⑤        写回 count = 1
  ⑥                                     写回 count = 1
----------------------------------------------------
最终：count = 1（预期是 2）

这里没有任何“读到了不该读的旧值”的问题：B 读的时候 A 还没写回 1，B 正常读取到 0。

同样也不需要发生指令重排。即使每个线程内部都严格按照“读、加、写”的源码顺序执行，只要两个线程在这三步之间交错，就会丢失更新。

2.2 为什么 A 写了 1 后，B 不会自动重新算一遍？

因为 B 早就把 0 取出来放进了本次计算的临时值，已经算出了 1。后面 A 对共享变量的写入，不会追溯修改 B 已经完成的计算。

volatile 没有规定“只要别人写了新值，我之前读出来的本地变量就必须自动重新计算”。这不是 volatile 的职责。

3. 精确定义：可见性、原子性、有序性分别负责什么？

概念 通俗说法 volatile 对 count++ 能做什么？
可见性 写了一个新值，别的线程后续怎样可靠地看到它？ 对 volatile 本身的读写提供规范定义的可见性保证。
原子性 整套读—改—写是否不可被竞争更新打断？ 不能。两个线程仍可先后读取同一个 0，再都写回 1。
有序性 哪些指令优化不能破坏规定的观察结果？ 为 volatile 读写建立发布/获取相关的顺序约束，但不禁止全部重排。

前一章 JMM 与 happens-before 讲的是A 的先前写入如何对 B 后续读取可见。

这一章讲的是另外一个问题：即使读写都可见，两个线程同时修改同一个值，是否会覆盖彼此的成果？

3.1 两个关键区别

  • volatile count = 1：这是一次写操作，没有“先读再算再写”的复合步骤。
  • volatile count++：这是一次复合操作，要先知道旧值才能计算新值，会出现并发竞争窗口。

因此不要把“volatile 保证可见性”背成“volatile 保证并发安全”。

为什么不能简单说“volatile 保证最新值”？

准确的说法是：volatile 读写遵循 Java 内存模型定义的同步顺序和可见性规则。它不会预知未来的写入，更不能阻止两个线程在任何写回发生之前都读到 0。

4. 用 Java 代码稳定复现丢失更新

很多示例让两个线程循环一百万次，然后说“你应该看到少于两百万”。这种写法只能说可能发生竞争，不保证每次运行都会出现特定数字。

为了第一次学习更直观，我们用两个 CountDownLatch 把执行顺序固定成：A、B 都先读完 0，然后再一起开始写回。

下面代码可直接保存为 VolatileLostUpdateDemo.java，在 Java 8 / Java 17 下编译运行：

import java.util.concurrent.CountDownLatch;

public class VolatileLostUpdateDemo {
    private static volatile int count = 0;

    public static void main(String[] args) throws InterruptedException {
        CountDownLatch bothRead = new CountDownLatch(2);
        CountDownLatch canWrite = new CountDownLatch(1);

        Runnable task = () -> {
            int oldValue = count; // A、B 都会先读到 0
            bothRead.countDown();
            try {
                canWrite.await(); // 等另一位线程也读完
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
                return;
            }
            count = oldValue + 1; // 两人都会把 1 写回
        };

        Thread a = new Thread(task, "A");
        Thread b = new Thread(task, "B");
        a.start();
        b.start();

        bothRead.await();     // 确认两人都拿到旧值
        canWrite.countDown(); // 允许两人写回
        a.join();
        b.join();

        System.out.println(count); // 1
    }
}

这段示例为什么能稳定得到 1？

  • 两个线程都在 count 更新前，先完成一次读取，因此都会拿到 0。
  • 主线程等两人读取结束才释放 canWrite；两人之后都执行 count = 0 + 1。
  • 两次写回的都是 1，所以最终还是 1。

注意： 这里故意把 count++ 拆开来控制交错，用于稳定证明复合操作会丢失更新；不是声称真实业务中的单行 count++ 每次都执行成这个固定顺序。

5. 修复方案一：AtomicInteger 原子递增

import java.util.concurrent.atomic.AtomicInteger;

public class AtomicCounterDemo {
    private static final AtomicInteger count = new AtomicInteger(0);

    public static void main(String[] args) throws InterruptedException {
        Runnable task = () -> count.incrementAndGet();
        Thread a = new Thread(task, "A");
        Thread b = new Thread(task, "B");
        a.start();
        b.start();
        a.join();
        b.join();

        System.out.println(count.get()); // 2
    }
}

AtomicInteger.incrementAndGet() 的承诺是：整个递增作为原子更新完成。当 A 和 B 都成功执行一次时，结果一定包含两次递增。

5.1 CAS 是什么？先理解“尝试，不允许乱覆盖”

CAS = Compare And Set，可以先记成“拿旧值核对一下，没变才写入”。

在上面的交互动画里，使用了一个 CAS 风格的概念过程：

  1. A 想把 0 → 1，成功。
  2. B 也想把 0 → 1，但现在真实值已是 1，所以这次尝试失败。
  3. B 重新基于 1 计算，尝试 1 → 2，成功。

它确保 B 不会像普通 count++ 那样，把 A 的更新无条件覆盖掉。

关于“源码级”和“概念级”的区别

这是用 CAS 解释原子更新的一条概念执行路径。AtomicInteger.incrementAndGet() 的具体底层实现会因 JDK 版本、JVM 和 CPU 而不同；现代 JDK 可能使用原子 get-and-add 等机制，不能把动画逐帧当成它真实执行的 Java 源码或机器指令。下一章会专门讲 compareAndSet()、CAS 循环和 ABA。

5.2 一个极容易写错的代码

AtomicInteger count = new AtomicInteger(0);

// 错误：两次操作分别是原子的，拼在一起不是！
count.set(count.get() + 1);

// 正确：整个递增具有原子性
count.incrementAndGet();

AtomicInteger 不是魔法容器；要选对它提供的原子操作。同理，get()、计算、set() 分开写，仍然可能丢失更新。

6. 修复方案二：synchronized 把整套步骤锁起来

public class SynchronizedCounterDemo {
    private static int count = 0;
    private static final Object LOCK = new Object();

    private static void addOne() {
        synchronized (LOCK) {
            count++; // 只有拿到同一把锁的人，才能进入这里
        }
    }

    public static void main(String[] args) throws InterruptedException {
        Thread a = new Thread(SynchronizedCounterDemo::addOne, "A");
        Thread b = new Thread(SynchronizedCounterDemo::addOne, "B");
        a.start();
        b.start();
        a.join();
        b.join();
        System.out.println(count); // 2
    }
}

可以把 synchronized 想成一间只有一把钥匙的操作室：

  • A 先拿到钥匙，就能在屋内读、加、写；此时 B 只能等。
  • A 归还钥匙后，B 才能进入，看到 A 完成的结果，再做第二次加一。
  • 必须保护的是同一份共享数据，并且竞争线程必须使用同一把锁。 A 锁 LOCK_A、B 锁 LOCK_B，对同一个 count 并没有形成互斥。

synchronized 也提供相应的可见性和 happens-before 保证：对一个监视器的解锁 happens-before 后续对同一个监视器的加锁。

7. 边界与常见误解

误解一：“volatile 已经读最新值，B 不应该再读到 0。”

B 读取时 A 可能还没有写回 1，所以 B 合法且正常地读到 0。随后 A 写回 1，并不会自动重做 B 已经执行的读取。

误解二：“丢失更新是 CPU 指令重排造成的。”

不一定。本节动画里完全不需要重排。仅仅因为两个线程的操作交错执行就能复现。

误解三：“AtomicInteger 的 get() 和 set() 都是原子的，所以 get()+set() 一起也是原子的。”

错误。每一个方法的单独原子性，不会自动扩大成整个 get → 计算 → set。

误解四：“加了 synchronized，就算两边锁不一样也安全。”

错误。A、B 必须用同一把锁，才能防止对共享变量的更新交错。

误解五：“AtomicInteger 比 synchronized 在所有场景下都更好。”

不成立。AtomicInteger 很适合单个数值的简单原子更新；如果要同时维护库存数、总金额等多个共享字段之间的一致性，同一个锁保护整个业务逻辑往往更直观。高竞争下的吞吐量也需要实际测量，不能光凭名字判断。

误解六：“线程启动了，我在 main 线程直接打印就一定能看到最终值。”

错误。打印前还要等待工作线程完成，例如用 join()；否则你可能在两个工作线程还没运行完时就打印。join() 负责等待和建立对应完成后的可见性，不能替代 count++ 本身所需的并发保护。

8. 面试怎么回答？

面试官：volatile 能保证可见性，为什么不能保证 count++ 的原子性？

count++ 不是一个不可分割的操作，逻辑上包括读取旧值、加一、写回。volatile 保证单次读写的内存可见性与相关有序性，但不会让读—改—写整体互斥。比如两个线程都在别人写回前读到 0，分别算出 1，最后都写回 1，就会丢失一次更新。解决可以用 AtomicInteger.incrementAndGet() 做原子更新，也可以用同一把锁上的 synchronized 把整个操作保护起来。

追问一：volatile int count 的单次读和写是不是原子的？

是。这里不安全的不是一次读取或一次赋值，而是 count++ 需要把多个步骤作为一个整体完成。

追问二：AtomicInteger 为什么不会丢失更新？

它提供原子的读—改—写操作，例如 incrementAndGet()；发生竞争时，更新不会默默覆盖掉别人已经完成的递增。CAS 重试可以帮助理解这一思想，但不能假定所有 JDK 都按动画中的 Java 代码逐步执行。

追问三：只要 synchronized 包住了 count++，就一定安全？

只有当所有可能并发修改这个共享 count 的路径都遵守同一把锁时，才能依靠这把锁保证这一更新过程的互斥。绕开锁的写入仍然会破坏约束。

多线程与 JMM · 第 3 节

CAS 与 ABA：明明检查了旧值，怎么还会改错？

上一节我们发现：两个线程都读取 count=0，再各自写回 1，会丢失一次递增。现在换一种思路：写入之前先问一句“它还是我刚才看见的那个值吗？”这就是 CAS 的出发点。

30 秒速懂

CAS = Compare-And-Set（比较并设置）。可以理解成售票员处理库存：

  • 我刚才看到余票是 5 张，准备改成 4 张。
  • 提交时重新核对：当前仍是 5 吗？ 是，才允许这次更新；不是，就报告失败。
  • 别人先把 5 改为 4，我再用旧的 5 去写，就不能悄悄覆盖别人的结果。

**但是：**如果库存经历了 5 → 3 → 5，只看“现在还是 5”会发现不了期间曾被修改，这就是 ABA 问题。

1. 反例：不核对旧值，更新就会丢

// 共享值当前为 0
int oldA = count;  // A 读到 0
int oldB = count;  // B 也读到 0
count = oldA + 1;  // A 写 1
count = oldB + 1;  // B 还是写 1：覆盖了 A 的成果

上面是概念性的交错步骤，不是可以直接复制运行的完整并发程序。核心问题是：B 从未检查它读取以后，count 有没有被其他线程改变。

使用 AtomicInteger.compareAndSet(expected, update) 时，比较与更新在并发意义上是同一次原子操作：

AtomicInteger atom = new AtomicInteger(0);
boolean ok = atom.compareAndSet(0, 1);
// 只有当前值仍是 0，才尝试改成 1；返回是否成功

它不是 Java 的 if (atom.get()==0) atom.set(1) 的简单缩写。后面这种写法的判断和写入之间可以被其他线程插入。

2. 动画：成功 → 失败 → ABA → 带版本号的修复

先看第一个模式，看 B 为什么不能直接覆盖 A；再切到 ABA，看“值绕一圈回到原样”的危险；最后看加上版本号后的效果。

2.1 一次 compareAndSet 失败，是否自动重试？

不会。 compareAndSet() 单次调用只告诉你成功或失败；要不要再次读取、重新计算并尝试，需要业务代码决定。

import java.util.concurrent.atomic.AtomicInteger;

public class CasLoopDemo {
    public static void main(String[] args) {
        AtomicInteger count = new AtomicInteger(0);

        // 这一段手写重试循环在 Java 8 / 17 都能运行
        for (;;) {
            int old = count.get();
            int updated = old + 1;
            if (count.compareAndSet(old, updated)) {
                break; // 成功，退出
            }
            // 失败说明尝试时已经不匹配；重新读取和计算
        }
        System.out.println(count.get()); // 1
    }
}

注意 AtomicInteger.incrementAndGet() 本身保证原子递增，实际 JVM/JDK 可能采用原子加指令或其他实现；不要认为它在所有平台上都恰好执行上面这段 Java 循环。

3. ABA 究竟是什么？

假设某个状态最初为 A：

时间向下：
线程 A                         线程 B
读到状态 A，准备改 C           —
暂时停住                       将 A 改为 B
                               又将 B 改回 A
CAS(预期 A, 新值 C) 成功        —

A 的 CAS 在原子性上没有出错：提交时当前值确实等于 A。但假设业务要求「从我检查起，这个对象从未被别人修改过」，单纯的值比较就不够了。

ABA 不是所有业务场景里的漏洞

如果你关心的只有当前计数值，而不关心中间改动的历史，那么 A → B → A 可能完全没问题。

危险场景通常是：业务正确性依赖“期间没有变更”，例如需要识别状态版本是否更新过、某个节点或资源是否经历过释放再复用。不能看到 ABA 三个字就断言所有 CAS 都不安全。

4. 为什么版本号能发现变化？

让状态从单独的 A 变成一对数据 (A, stamp=0)：

A 首次读取       (A, 0)
B 修改第一次     (B, 1)
B 修改第二次     (A, 2)
A 想提交时对比   预期 (A,0) ≠ 当前 (A,2)
结果             CAS 失败

在 Java 8 / 17 中，AtomicStampedReference<V> 支持同时比较引用与版本戳：

import java.util.concurrent.atomic.AtomicReference;
import java.util.concurrent.atomic.AtomicStampedReference;

public class AbaDemo {
    enum State { A, B, C }

    public static void main(String[] args) {
        // 场景 1：只比较引用，无法识别从 A → B → A 的历史
        AtomicReference<State> normal = new AtomicReference<>(State.A);
        State old = normal.get();              // A 先观察到 A
        normal.set(State.B);                   // 模拟 B 修改
        normal.set(State.A);                   // 模拟 B 又改回来
        System.out.println(normal.compareAndSet(old, State.C)); // true

        // 场景 2：除了引用，还检查版本号
        AtomicStampedReference<State> tagged =
                new AtomicStampedReference<>(State.A, 0);
        int[] holder = new int[1];
        State oldRef = tagged.get(holder);     // 原子地取得引用+stamp
        int oldStamp = holder[0];              // 0

        tagged.compareAndSet(State.A, State.B, 0, 1);
        tagged.compareAndSet(State.B, State.A, 1, 2);
        System.out.println(tagged.compareAndSet(
                oldRef, State.C, oldStamp, oldStamp + 1)); // false
    }
}

运行输出固定为：

true
false

这段程序用串行操作固定模拟了 A 暂停、B 改动、A 继续的交错，方便稳定说明原理。真正的并发程序仍需要处理重试、冲突和线程退出等问题。

4.1 一个源码级细节：比较的是引用，不是 equals

AtomicStampedReference 的引用比较使用 ==（是否为同一个对象引用），不是对象的 equals()。所以如果业务状态是“内容相同但不同实例”的对象，不能直接用 equals 的心智模型解释它。上面使用 enum State，正好避免了“值相同但对象身份不同”的干扰。

4.2 版本号并非万能

  • stamp 是整数。如果版本策略设计不当、发生回绕或被业务代码错误复用，仍可能失去辨别能力。
  • 只能保护这一对引用与版本的原子更新；并不自动保护数据库另一行、外部支付服务或多个独立对象组成的事务。
  • 发生 CAS 失败时，业务应重新验证前提，不能无脑循环到成功，尤其是退款、扣款等有副作用的流程。

5. CAS 有什么代价？

问题 怎么理解
高竞争下重复失败 很多线程同时提交同一个旧值，失败方可能花时间重复计算与尝试。
ABA 只有当前值的比较，无法记录“中途被改过”的历史。
多变量一致性 单个 CAS 不能天然把两个独立账户的金额更新成一个原子事务。
自旋 ≠ 一定无阻塞 CAS 是原子原语，外层重试循环可能一直竞争；整体算法是否 lock-free 还取决于算法性质。

单个热点计数器可考虑 AtomicInteger；高并发统计还可了解 LongAdder（它的汇总语义和单次原子快照并不相同）。涉及一组需要同时一致的字段时，锁或事务往往更好解释与维护。

6. 面试怎么回答？

面试官：CAS 是什么，解决什么问题？

CAS 是 Compare-And-Set：比较期望旧值与当前值，匹配才原子写入新值，不匹配就失败。它能避免简单读—改—写在竞争时悄悄覆盖别人的成功更新。单次 CAS 失败不会自动重试，通常由上层决定重试逻辑。

追问：ABA 是什么？

A 线程先读到状态 A，B 线程把状态改为 B 又改回 A。A 再 CAS 时只看当前还是 A，可能成功，却没有识别期间变化。如果业务必须检测修改历史，可引入版本号，如 AtomicStampedReference 同时对比引用和 stamp。

追问：AtomicStampedReference 彻底解决所有并发问题吗？

不能。它只原子管理单个引用和版本戳，不是数据库事务。版本还要正确维护；CAS 失败要按业务重新校验。

AQS 与锁：抢不到锁，线程去哪儿了？

你已经知道：用同一把锁保护 count++ 能避免丢失更新。接下来问一个更底层的问题：线程 A 正在持锁，线程 B 也想进来时，B 是一直站着疯狂检查，还是会排队等通知？AQS 的价值是提供获取、等待、唤醒等同步基础机制，供锁等同步器复用。

30 秒速懂

把 ReentrantLock 想成一个只有一把钥匙的房间：

  1. A 先取得钥匙，进入房间。
  2. B 来了拿不到，就登记到等待队列，条件合适时阻塞等待。
  3. A 离开并放回钥匙，系统通知后面等待的人。
  4. B 被唤醒后还需要重新尝试拿钥匙；被叫醒 ≠ 已拿到钥匙。

AQS（AbstractQueuedSynchronizer）可以把状态记录、等待队列和唤醒机制封装起来。ReentrantLock 的同步实现使用了 AQS，但它自身还有公平/非公平策略、持锁者、可重入等语义。

1. 反例：不同的锁锁不住同一个共享变量

private static int count = 0;
private static final Object LOCK_A = new Object();
private static final Object LOCK_B = new Object();

// 线程 A
synchronized (LOCK_A) { count++; }

// 线程 B
synchronized (LOCK_B) { count++; }

错误原因： 两边虽然都写了 synchronized，但互斥的单位是同一个监视器对象。A 用 LOCK_A，B 用 LOCK_B，它们可以同时进入各自的临界区。

ReentrantLock 也一样：所有竞争线程必须使用同一个锁实例来保护同一份共享数据。

2. 动画：等待队列、重入计数和非公平插队

先选择「锁竞争」模式，跟着 A 持锁、B 入队、A 解锁、B 重新获取；再尝试「可重入」和「非公平插队」。

3. AQS 管理哪些东西？

可以先记住三件事，不必马上硬背全部节点字段：

组成 直观理解 与 ReentrantLock 的关系
state 一个整型同步状态 独占锁中常表示持有/重入次数，0 通常为空闲。
等待队列 抢不到资源的人登记排队 获取失败的线程可能入队、阻塞，等待后续唤醒。
获取/释放模板 不同同步器共用排队唤醒机制 由具体同步器规定 tryAcquire / tryRelease 等尝试逻辑。

AQS 的核心不是一个“谁先排队谁一定先拿到锁”的万能队列。它通过状态检查、原子更新、队列和 park/unpark 等机制协调竞争者。

3.1 一个简化的独占获取过程

线程 B 想 lock()
  ↓
尝试获取锁（tryAcquire）
  ├─ 成功 → 进入临界区
  └─ 失败 → 进入 AQS 等待队列
               ↓
           根据条件等待 / park
               ↓
        被通知或其他原因返回
               ↓
        再次检查获取条件
               ├─ 成功 → 进入临界区
               └─ 失败 → 继续等待 / 重试

这里的 park 可能被唤醒，也可能出现允许的无理由返回，所以等待方需要循环检查条件。不能把 unpark 简化成“精准地把锁所有权交给 B”。

3.2 为什么叫“可重入”？

ReentrantLock lock = new ReentrantLock();
lock.lock(); // 第一次：当前线程获得锁，计数 1
lock.lock(); // 第二次：同一线程再次获得，计数 2
try {
    // 只有当前线程能进入的工作区
} finally {
    lock.unlock(); // 计数减为 1
    lock.unlock(); // 计数减为 0，完全释放
}

同一个线程重复获取自己的锁不会因为自己的锁而阻塞；但每次成功 lock() 都必须有对应的 unlock()，否则锁可能永远不释放。

实际业务不要手工到处配对两次，尽量把每次获取与释放放到清楚的 try/finally 生命周期内。

4. 公平锁和非公平锁到底差在哪？

ReentrantLock nonfair = new ReentrantLock();     // 默认非公平
ReentrantLock fair = new ReentrantLock(true);    // 选择公平策略
  • 非公平：可能允许新到的线程趁锁刚释放时先拿到锁，即使已有等待者；这叫 barging（插队）。
  • 公平：通常会优先考虑等待时间更久的竞争者；但不保证操作系统按理想顺序调度，更不能声称任何 API 调用都绝对 FIFO。
  • 例如无超时的 tryLock() 在公平锁上也可以立即获取可用锁，而不严格遵循公平等待顺序——这是 API 的明确语义。
常见误区：AQS 队列是 FIFO，所以 ReentrantLock 必须先来先得？

不对。等待队列有顺序，并不代表每次锁获取都严格按顺序成功。非公平锁允许竞争插队；即使公平策略也受具体 API 与调度影响。把“队列次序”和“拿锁顺序”区分开。

5. Java 8 / 17 可运行例子：一把锁保护 count

import java.util.concurrent.locks.ReentrantLock;

public class ReentrantLockDemo {
    private static final ReentrantLock LOCK = new ReentrantLock();
    private static int count = 0;

    static void add() {
        LOCK.lock();
        try {
            count++; // 整个读—加—写都在锁里
        } finally {
            LOCK.unlock(); // 即使发生异常，也必须释放
        }
    }

    public static void main(String[] args) throws InterruptedException {
        Thread a = new Thread(ReentrantLockDemo::add, "A");
        Thread b = new Thread(ReentrantLockDemo::add, "B");
        a.start();
        b.start();
        a.join();
        b.join();
        System.out.println(count); // 2
    }
}

为什么结果是 2？

  1. 同一个 LOCK 实例保护两次操作。
  2. A 或 B 先拿锁都无所谓；另一个必须等待已经持锁的线程释放。
  3. 两次受保护的递增最终都会执行一次。
  4. 主线程通过 join() 等两者结束，再观察结果。

lock() 遇到竞争时的阻塞与唤醒，不需要业务自己写一个 while(true) 狂转。注意 ReentrantLock 也提供 lockInterruptibly()、tryLock()、Condition 等能力；不同方法的等待和中断语义有差别。

6. AQS 与 synchronized 有什么区别？

角度 synchronized ReentrantLock
基础实现 JVM 监视器机制 Java 类库同步器，内部依赖 AQS 等机制
释放方式 退出同步块自动释放 通常必须在 finally 手动 unlock()
可重入 支持 支持
可中断地等待锁 没有同样形式的直接 API 有 lockInterruptibly()
定时尝试锁 没有直接对应形式 有 tryLock(timeout, unit)
公平策略选择 没有公开构造参数 可用 new ReentrantLock(true)

不要把 synchronized 说成“永远很慢”，也不要说 ReentrantLock 一定更快。性能和可控性取决于具体竞争方式、JDK 实现和业务场景。

7. 边界和面试常见陷阱

  • “B 被唤醒等于 B 直接持有锁”：错误。它仍需再次满足获取条件。
  • “state=0/1 是 AQS 在所有子类的唯一含义”：错误。Semaphore、CountDownLatch 等同步器对 state 的解释不同。
  • “AQS 只适合独占锁”：错误。它还支持共享获取模式，某些同步器使用共享模式。
  • “公平锁完全杜绝饥饿或严格保证 FIFO”：过度承诺。公平锁偏向排队者，但具体 API 与系统调度仍有边界。
  • “unlock 可以少写一次”：错误。重入次数要匹配，否则会一直持锁。
  • “用两个不同锁保护一个变量也安全”：错误。所有修改路径要遵循同一互斥规则。

8. 面试怎么回答？

面试官：AQS 是什么？

AQS 是 Java 并发包里构建同步器的基础框架。它维护同步状态，并提供等待队列、线程阻塞与唤醒的公共机制；具体同步器实现尝试获取或释放状态的逻辑。ReentrantLock 可以借助 AQS 实现独占锁及其排队等待行为。

追问：抢不到 ReentrantLock 会发生什么？

线程先尝试获取锁；失败后可能加入 AQS 等待队列，根据条件阻塞。持锁者释放时会触发相应唤醒，等待线程醒来后还要重新检查并竞争锁，不是直接被分配锁。

追问：为什么 ReentrantLock 可重入？

锁记录当前独占持有线程和同步状态。相同线程再次获取时可以增加重入计数；解锁逐次减少，直到计数归零才完全释放。

线程池 execute()：为什么有时排队，有时创建线程，有时拒绝？

想象一家餐厅：固定有一位厨师（核心线程），门口只有一个等候位（有界队列），生意太忙还能临时请一位厨师（扩展线程）。当厨师和等候位都满了，新来的订单会怎样？这就是 ThreadPoolExecutor.execute() 处理任务的核心问题。

30 秒速懂

ThreadPoolExecutor 的典型 execute(task) 路线：

  1. 工作线程数少于 corePoolSize：先尝试创建核心工作线程执行任务。
  2. 否则：线程池还在运行时，尝试把任务放入工作队列。
  3. 队列放不进去：尝试在 maximumPoolSize 上限内创建更多线程。
  4. 已经无法接收：执行拒绝策略。

所以：不是“任务一来就先扩容到 maximumPoolSize”；通常先达到核心线程数，再排队，队列满了才考虑扩容。

1. 反例：明明 max=100，为什么只有 2 个线程忙？

ExecutorService pool = new ThreadPoolExecutor(
        2, 100, 30, TimeUnit.SECONDS,
        new LinkedBlockingQueue<Runnable>());

不少人以为这个线程池在 2 个线程忙不过来时会自动创建 100 个线程。通常不会：这里无参 LinkedBlockingQueue 的容量是 Integer.MAX_VALUE，任务优先排队，offer() 一般不会因为业务积压而失败。除非出现极端条件，线程池很难走到“队列满，扩容到 max”那条分支。

后果是：队列可能越来越长，占用内存，而不是自动扩容把积压消化掉。 这也是生产系统常见的线程池误配置。

2. 交互流程：分别模拟有界、无界和关闭

点“有界队列”中的四个提交步骤，看 T1、T2、T3、T4 分别去了哪里。然后切换“无界队列”，观察 max 为什么长期发挥不了作用。

3. execute() 到底按什么条件判断？

下面是用中文缩写的控制流程，不是对特定 JDK 源码逐字复制：

                       execute(task)
                             │
                  workerCount < core ?
                      ┌──────┴───────┐
                     是              否
                      ↓              ↓
             addWorker(task)   pool 运行中 && queue.offer(task) ?
                   │                 ├─ 是 → 二次检查池状态 / worker 数
                   └─ 成功返回       │        ├─ 已 shutdown 且能移除任务 → reject
                                     │        └─ 无 worker → 尝试启动 worker
                                     └─ 否 → addWorker(task, 非核心上限 max)
                                                   ├─ 成功 → 执行任务
                                                   └─ 失败 → reject

为什么入队成功以后还要重新检查线程池状态？因为入队的一瞬间池可能从 RUNNING 变成 SHUTDOWN。execute() 并不能只依据入队前看到的状态，决定这个任务一定已被合法接收。

还有一种细节：任务排队成功但工作线程数量为 0 时，要尝试启动一个没有首任务的 worker 去消费队列；否则任务可能一直没人取。

3.1 这五个参数分别负责什么？

参数 通俗理解 容易答错的地方
corePoolSize 核心工作线程数量阈值 默认不一定在创建线程池时就立刻建好。
maximumPoolSize 线程数的总上限 包括核心线程，不是“额外线程数量”。
workQueue 放不下当前直接执行的任务先排队 队列容量直接改变扩容与拒绝路径。
keepAliveTime 非核心空闲线程等待任务的超时时间 默认主要约束超出核心数的空闲线程；可设置允许核心超时。
RejectedExecutionHandler 接不下新任务时如何处理 拒绝不一定会抛异常，取决于策略。

3.2 四种标准拒绝策略

策略 行为 风险
AbortPolicy 抛 RejectedExecutionException 调用方没处理可能导致请求失败。
CallerRunsPolicy 在未关闭等条件满足时，由提交线程直接运行任务 能形成背压，但阻塞提交线程，甚至拖慢 HTTP 请求线程。
DiscardPolicy 静默丢弃被拒绝的任务 无感知丢任务，业务风险高。
DiscardOldestPolicy 尝试丢弃队头任务，再提交当前任务 可能丢旧任务；关闭、持续满载等情况须额外考虑。
特别注意：CallerRunsPolicy 不是绝对不丢任务

标准 CallerRunsPolicy 在执行器未关闭时，才由调用线程运行任务。如果执行器已经关闭，它不会帮你执行这个任务。所以绝不能把它写成“所有拒绝任务都能被主线程兜底执行”。

4. 一段可以稳定看到「入队 → 扩容 → 拒绝」的 Java 代码

下面为 Java 8 / Java 17 可运行示例。两个执行中的任务故意等待门闩，因此输出的拒绝结果是稳定可复现的（普通日志打印先后不依赖固定线程调度）。

import java.util.concurrent.*;

public class PoolRouteDemo {
    public static void main(String[] args) throws InterruptedException {
        CountDownLatch release = new CountDownLatch(1);
        ThreadPoolExecutor pool = new ThreadPoolExecutor(
                1, 2, 60, TimeUnit.SECONDS,
                new ArrayBlockingQueue<Runnable>(1),
                new ThreadPoolExecutor.AbortPolicy());

        Runnable blocker = () -> {
            try {
                release.await(); // T1、T3 一直忙，直到主线程放行
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        };

        try {
            pool.execute(blocker);            // T1：创建核心 worker
            pool.execute(() -> {});            // T2：进队列
            pool.execute(blocker);             // T3：队列满，扩容 worker
            try {
                pool.execute(() -> {});        // T4：队列满、线程达到 max
                System.out.println("T4 accepted");
            } catch (RejectedExecutionException e) {
                System.out.println("T4 rejected"); // 稳定打印
            }
        } finally {
            release.countDown();
            pool.shutdown();
            if (!pool.awaitTermination(5, TimeUnit.SECONDS)) {
                pool.shutdownNow();
            }
        }
    }
}

输出关键行： T4 rejected。

为什么 T2 不会抢先执行导致不同结果？T1 被门闩阻塞、单个核心 worker 在忙；T2 必须先占据容量 1 的队列；T3 再触发创建第二个 worker 并在门闩处等待。提交 T4 时队列和工作线程名额均已占满。

5. 线上如何选择线程池参数？

先看任务类型，再看阻塞时长、目标吞吐、延迟、下游承载能力、内存预算，而不是背一个固定的“CPU 核心数 × 2”。

  • CPU 密集型：过多线程会增加上下文切换，通常从接近可用 CPU 数量的规模开始压测。
  • IO 等待明显：线程数可能大于 CPU 数量，但必须同时考虑数据库连接池、HTTP 连接、Kafka Consumer 对象及下游限流能力。
  • 短任务高流量：队列必须有明确容量与饱和处理方式；排队时间也是延迟的一部分。
  • 任务可能永久阻塞：线程和队列容量再大也不能从根本上解决，需要超时、隔离、取消和监控。

需要持续监控 getActiveCount()、getPoolSize()、getQueue().size()、getCompletedTaskCount()、拒绝次数，以及任务排队时间。监控读数是运行时快照，不保证多个指标来自同一瞬间。

6. shutdown、shutdownNow、submit 与 execute

shutdown()：拒绝新任务，已经提交的任务仍有机会执行完成；不会等待它们结束。awaitTermination() 可以用于等待。

shutdownNow()：尝试中断正在运行的任务，返回尚未开始执行的排队任务列表；不保证能强制停止忽略中断的任务。

execute(Runnable)：提交一个没有结果的任务。饱和时 AbortPolicy 的拒绝异常从调用点抛出。任务自身抛异常会交给工作线程的异常处理机制。

submit(...)：返回 Future，可获得结果和异常；任务运行异常通常通过 Future.get() 的 ExecutionException 表现，不能以为“没看到工作线程日志 = 成功”。

7. 边界和误解

  • “线程池总是先创建 max 个线程”：错。队列策略优先级很关键。
  • “无界队列不会 OOM”：错。大量排队任务占用堆内存。
  • “maximumPoolSize 就是最大额外线程数”：错，是工作线程总数上限。
  • “线程池已关闭还能加任务，只要队列有空间”：错，会拒绝新提交。
  • “线程越多吞吐一定越大”：错。下游连接数、CPU、锁竞争可能先成为瓶颈。
  • “任务超时就可以强制杀死线程”：错。Java 中断是协作式机制，不保证任务立即退出。

8. 面试怎么回答？

面试官：ThreadPoolExecutor.execute() 的流程？

先看工作线程数是否小于 corePoolSize，是就尝试新增核心 worker；否则在线程池仍运行时尝试入队。入队成功需要二次检查池状态并确保至少有 worker 消费队列。入队失败再尝试在 maximumPoolSize 内扩容。扩容失败或不能接收时走拒绝策略。所以队列类型直接影响扩容路径。

追问：设置 core=10、max=100，为什么线程数一直只有 10？

如果使用默认容量很大的 LinkedBlockingQueue，超过核心数的任务通常直接排队，队列不满就不会触发新建非核心 worker 的分支。风险是积压和内存消耗，并非配置错了 max 数值本身。

追问：你们生产为什么要使用有界队列？

主要是为排队和内存设置上界，并在系统过载时让拒绝/背压策略及时暴露问题。具体容量、线程数要通过任务等待时间、目标吞吐和下游能力压测，而不是拍脑袋。

ThreadLocal 与 CompletableFuture：为什么异步线程拿不到我的用户信息？

做 Java 后端时，你可能把当前用户、traceId 等上下文放入 ThreadLocal，并在一个请求里随时读取。问题来了：线程池会复用工作线程，而 CompletableFuture 又可能把任务切到另一个线程。你放进去的值到底跟着“请求”走，还是跟着“线程”走？

30 秒速懂
  • ThreadLocal：像每个工作人员自己的储物柜。线程 A 存的东西，线程 B 不会自动拿到；柜子属于线程，不属于一次请求。
  • 线程池复用：同一个工作人员可能连续处理两个用户。如果上一次忘记清理储物柜，下一次可能读到旧用户的数据。
  • CompletableFuture：像把工作单交给别人去做。工作单可以携带明确参数，但不会自动搬走你自己柜子里的所有物品。

核心原则：ThreadLocal 要 set / try / finally remove；异步业务上下文优先显式传参。

1. 反例：一个线程先处理 A，再处理 B

static final ThreadLocal<String> USER = new ThreadLocal<>();

// 同一个线程池 worker 先执行任务 1
USER.set("用户 A");
// ...任务结束，却没有 remove()

// 同一个 worker 又执行任务 2
System.out.println(USER.get()); // 如果任务 2 没有先 set，可能读到「用户 A」

ThreadLocal 不是“任务隔离变量”。它是“线程隔离变量”。只要线程池复用同一个工作线程，旧的 ThreadLocal 条目可能继续保留，造成跨请求污染，严重时会把 A 用户的上下文带入 B 的处理流程。

2. 动画：错误复用 → finally 清理 → 异步切线程

第一种场景看同一 worker 复用导致的错误；第二种看为什么 remove() 有用；第三种看主线程的 ThreadLocal 为什么不会自动传进 CompletableFuture 的异步线程。

3. ThreadLocal 的数据到底存在哪里？

你可以先用下图建立概念模型：

Thread-1 ──> ThreadLocalMap-1
                   └── (ThreadLocal USER) → "A"

Thread-2 ──> ThreadLocalMap-2
                   └── (ThreadLocal USER) → "B"

两个线程访问的是同一个 ThreadLocal 对象，但通过当前线程找到的映射不同。ThreadLocal 本身并不是装着一个共享的 String 字段，供线程去抢读写。

3.1 为什么可能出现内存泄漏？

在经典的 ThreadLocalMap 实现中，条目的 key 持有 ThreadLocal 的弱引用，而 value 是强引用：

线程活着 ─→ ThreadLocalMap ─→ Entry
                              ├─ key: 弱引用 → ThreadLocal
                              └─ value: 强引用 → 大对象 / 用户上下文

假如业务丢掉了对 ThreadLocal 对象的其他强引用：

  1. GC 可能清除弱引用的 key，让它变成 null。
  2. value 不会因此必然立刻释放，因为它仍被 ThreadLocalMap.Entry 强引用。
  3. 后续在 ThreadLocalMap 上的相关操作可能清理这些陈旧条目，但不能依赖某个固定时间点自动清理。
  4. 在线程池里，线程生命周期长，因此滞留对象或旧上下文的危害更加明显。

即使 ThreadLocal 本身被声明为 static final，不会轻易丢失 key，不 remove 也仍然可能导致跨任务数据污染、持有不再需要的对象。所以清理不仅仅是防止“key 变 null”这一种问题。

4. 正确写法：try / finally / remove

private static final ThreadLocal<String> USER = new ThreadLocal<>();

void handle(String userId) {
    USER.set(userId);
    try {
        doBusiness(); // 同一线程内可以 USER.get()
    } finally {
        USER.remove(); // 不论成功、失败，都执行清理
    }
}

注意这是作用域约束：所有进入这个上下文的入口都必须保证清理；而不是“创建了 ThreadLocal 就全局线程安全”。如果 doBusiness 内部切换到其他线程，那个线程不会自动继承这里的 USER 值。

5. CompletableFuture 为什么可能切换线程？

CompletableFuture<T> 可以表示一个将来完成的值，并用链式方法编排后续处理：

CompletableFuture.supplyAsync(() -> queryUser(id), executor)
        .thenApply(user -> user.getName())
        .exceptionally(ex -> "fallback");

要分清楚几个常见方法：

API 作用 线程语义
supplyAsync(supplier, executor) 异步执行、有返回值 使用传入的 executor。
runAsync(runnable, executor) 异步执行、无返回值 使用传入的 executor。
thenApply(fn) 转换上一步结果 非 Async：可能由完成上一阶段的线程或其他调用线程执行，不要假定固定线程。
thenApplyAsync(fn, executor) 用指定执行器安排转换 由 executor 执行；不保证每次创建新线程。
thenCompose(fn) 把“返回 Future 的函数”展开成单层链 和 thenApply 的返回结构不同。
thenCombine(other, fn) 合并两个 Future 的结果 通常等待二者都正常完成再执行合并函数。
exceptionally(fn) 失败后的降级处理 处理异常完成结果；异常链路仍要考虑执行阶段。
join() / get() 获取最终结果 都可能等待；异常包装与受检异常声明不同。

没有显式传 executor 的 *Async 方法通常使用默认异步执行设施，常见是 ForkJoinPool.commonPool()；不要依赖它一定在某个固定线程执行，也不能当成“每提交一次就开一个新线程”。

5.1 为什么 ThreadLocal 不会自动跟着 CompletableFuture 跑？

USER.set("张三"); // main 线程
CompletableFuture.supplyAsync(() -> USER.get(), executor);

异步任务可能在工作线程 W 上执行，W 查的是自己的 ThreadLocalMap。如果 W 没有对应值，get() 默认可能返回 null；如果 W 曾经残留旧值，可能读到错误的旧值。无论哪种，都不能假设它等于 main 线程刚设置的“张三”。

推荐显式传递不可变业务参数：

String userId = USER.get(); // 在提交任务之前读取上下文
CompletableFuture<String> future =
        CompletableFuture.supplyAsync(() -> queryUser(userId), executor);

这样异步任务依赖什么数据，在参数里一目了然。如果确实要用上下文传播框架，也需要明确传播、恢复和清理规则，并注意线程池复用。

6. Java 8 / Java 17 可运行演示：线程池残留与异步传参

下面只用一个固定工作线程，确保它会复用，输出不会依赖线程池碰巧选择哪一个 worker。

import java.util.concurrent.*;

public class ThreadLocalFutureDemo {
    private static final ThreadLocal<String> USER = new ThreadLocal<>();

    public static void main(String[] args) throws Exception {
        ExecutorService pool = Executors.newSingleThreadExecutor();
        try {
            // 任务 A 留下线程上下文（错误示范）
            pool.submit(() -> USER.set("A")).get();
            System.out.println(pool.submit(() -> USER.get()).get()); // A

            // 清理同一个 worker 的映射
            pool.submit(() -> USER.remove()).get();
            System.out.println(pool.submit(() -> USER.get()).get()); // null

            // main 设置 USER，工作线程不会自动得到 main 的值
            USER.set("main-user");
            try {
                System.out.println(pool.submit(() -> USER.get()).get()); // null
                String userId = USER.get(); // 明确从 main 取参数
                CompletableFuture<String> future = CompletableFuture.supplyAsync(
                        () -> "hello, " + userId, pool);
                System.out.println(future.join()); // hello, main-user
            } finally {
                USER.remove();
            }
        } finally {
            pool.shutdown();
            if (!pool.awaitTermination(5, TimeUnit.SECONDS)) pool.shutdownNow();
        }
    }
}

预期输出：

A
null
null
hello, main-user

6.1 用 CompletableFuture 处理异常

CompletableFuture<String> result = CompletableFuture
        .supplyAsync(() -> {
            throw new IllegalStateException("remote failed");
        }, pool)
        .thenApply(value -> "结果=" + value)
        .exceptionally(ex -> "降级结果");

System.out.println(result.join()); // 降级结果

要关注：join() 抛出的未处理异常通常是 CompletionException 之类的包装，get() 则使用 ExecutionException 等受检异常机制；不要误以为 join() 没有可能失败。

7. 常见误解与生产边界

  • “ThreadLocal 的值属于一次 HTTP 请求”：错。它属于线程，不会自动按请求清理。
  • “线程池 worker 执行完任务就被销毁”：错。通常会复用。
  • “ThreadLocal 的弱引用 key 使 value 必然被自动立即回收”：错。value 仍可能被 Entry 强引用。
  • “CompletableFuture 会自动传播父线程的 ThreadLocal”：错。普通 ThreadLocal 没这个保证。
  • “InheritableThreadLocal 能完美解决线程池传播”：错。它主要发生在线程创建的继承阶段，线程池重用时容易出现陈旧上下文。
  • “thenApply 一定在主线程，thenApplyAsync 一定新建线程”：都错。要区分阶段完成时机与执行器。
  • “异常只影响当前 Future，不需要监控”：错。异步链上的异常若没有观察/处理，业务可能默默未完成预期流程。

8. 面试怎么回答？

面试官：ThreadLocal 为什么在线程池里容易出问题？

ThreadLocal 的数据放在每个线程关联的 ThreadLocalMap 中。线程池会复用工作线程，一个任务的值不会随任务结束自动清理；后续任务如果忘了覆盖或清理，可能读到旧值。长期持有大对象还可能增加内存滞留。一般用 set / try / finally remove 确保任务范围结束就清理。

追问：ThreadLocal 为什么可能造成内存泄漏？

经典 ThreadLocalMap 的 Entry key 是弱引用，value 是强引用。key 可能被回收而 value 仍被 Entry 持有，直到相关清理操作发生。如果对应线程长期存活，就可能有较长时间的内存滞留；所以不能依赖 GC 代替 remove。

追问：CompletableFuture 的 thenApply 和 thenApplyAsync 区别？

thenApply 不要求一定异步调度，可能由完成阶段的线程执行；thenApplyAsync 使用异步执行策略，可显式传 Executor 控制线程池。两者都不能自动保证普通 ThreadLocal 在跨线程时传播，业务参数最好显式传递。
