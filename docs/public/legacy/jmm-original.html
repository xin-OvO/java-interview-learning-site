01 / 从真实问题开始先不讲术语
THE QUESTION

线程 A 写了 42，线程 B 就一定能读到吗？

假设有两个线程：A 负责写数据，B 负责读取。你可能会觉得，A 已经执行完赋值，B 当然能看到。但多线程里，不能这么推断。

原始代码 · 没有同步
int data = 0; boolean ready = false; // 线程 A data = 42; ready = true; // 线程 B if (ready) { System.out.println(data); }
你期望发生什么？

线程 A 先写 data = 42，再写 ready = true。B 如果看到 ready == true，似乎就该读到 42。

!
问题：上面两段代码没有建立跨线程的同步关系。即使 B 看到了 ready=true，也不能保证同时看到最新的 data。

先记住一句人话

同一段代码，在一个线程内部看起来有顺序；但跨线程时，没有同步就不能只根据“谁先执行”推断另一个线程一定看到了什么。
02 / JMM 的定义把术语翻译成人话
JAVA MEMORY MODEL

JMM 不是“内存长什么样”，而是“读写要守什么规则”

JMM 全称 Java Memory Model，Java 内存模型。它不告诉你变量存在哪个 CPU 缓存层里，而是规定：多个线程访问共享变量时，什么结果是允许的、什么结果必须得到保证。

物理世界（真实机器）
CPU 核心缓存内存

硬件如何缓存、刷新，和具体处理器、JIT 编译器等实现有关。

JMM（语言规范）
可见性有序性happens-before

写 Java 程序时，我们依赖这些规则，而不是猜具体硬件何时刷新缓存。

✓
类比交通规则：交通法规规定“红灯必须停”，但不规定你的车是油车、电车，也不规定刹车片内部怎么工作。JMM 也是这种“行为规范”。

JMM 常见的三个关键词

① 可见性

A 改了变量，B 能不能按规则看到这次修改？

visibility
② 有序性

编译器和 CPU 可能重排执行顺序；JMM 限制哪些重排可被其他线程观察到。

ordering
③ 原子性

某个操作能否整体完成、不会被其他线程“插队”造成中间状态？count++ 不具备原子性。

atomicity

严格地说，JMM 核心是对读写行为及同步的语义约束。面试中常用“可见性、有序性、原子性”整理并发问题。

第一次见 happens-before，先不要把它理解成“时间先后”

A happens-before B（简写 A → B），意味着 JMM 规定了 A 相对于 B 的顺序与可见性保证。在“写入 + 读取”的场景下，B 不能无视按此关系应当可见的 A 的写入。

A happens-before B ≠ “墙上时钟显示 A 比 B 早”

例如：A 在昨天改了普通变量，但今天另一个线程读取它——时间隔得很久，也不能因为过了很久就推导出两者存在 happens-before 关系。

!
重要限定：happens-before 不保证读操作必然读到某个特定的历史值；如果中间还有其他合法写入、数据竞争或读取顺序，需要结合整个执行关系判断。本课程的例子默认只有一个写入者。

04 / 规则卡片点击每个规则查看例子
RULES YOU ACTUALLY USE

happens-before 的常见规则

不建议硬背英文术语。先看代码中哪两个动作，为什么可以连上一条箭头。

① 同一线程内，前面的动作 → 后面的动作

只看同一个线程的程序顺序。例如先写 data，再写 ready，在 happens-before 关系上，前者先于后者。

A: data = 42 → A: ready = true
注意：这不等于 CPU 必须严格按照源代码逐条执行指令。JMM 允许不破坏其语义的优化。

常见误解：用 sleep 或“等一会”能保证可见性吗？

×
不能。 Thread.sleep(1000) 只让当前线程暂时不运行，它本身不为两个线程建立 happens-before 关系；在代码中靠睡眠协调线程，是非常脆弱的设计。

同理，Thread.yield()、单纯检查线程“看上去结束了”、根据日志时间推测“已经写完”都不等于建立了同步关系。

05 / 第二个关键陷阱可见不代表不会丢
RACE CONDITION

volatile 能看到新值，为什么 count++ 还是不安全？

因为 count++ 不是一个不可分割的动作。它大致包含：读当前值 → 加 1 → 写回新值。两个线程可能都读到相同的旧值。

即使 count 声明成 volatile，仍然会丢失更新
volatile int count = 0; // 线程 A、线程 B 都做 count++; // 这不是原子操作！

结论：volatile 能提供特定的可见性和有序性保证，但不能把复合的 count++ 变成原子操作。

那应该怎么改？

方案 1 · AtomicInteger
AtomicInteger count = new AtomicInteger(0); count.incrementAndGet();

单个计数器递增通常首选原子类，底层使用 CAS 等机制；大量竞争下还要关注性能。

方案 2 · synchronized
int count = 0; synchronized void add() { count++; }

使用同一把锁让递增操作互斥执行；适用于一组需要维护一致性的共享状态。

✓
记忆：volatile 是“信号灯 / 可见性”，锁与原子类是解决“大家同时修改同一个值”的常用工具。
06 / 自测用三道题检验是否真正理解
KNOWLEDGE CHECK

这三道题答对，才算入门

1. 线程 A 普通变量赋值后，休眠 1 秒，再让 B 读取：一定看得到新值吗？

正确。是否存在可见性保证，要看同步关系，而不是看经历了多久。

2. data 是普通 int，ready 是 volatile boolean；B 读到 ready=true 后读取 data。假设只有 A 写 data，能保证读到 A 先前写入的值吗？

正确。volatile ready 建立发布-读取关系，在例子的限定条件下足以保证 data 的可见性。

3. 将 count 声明为 volatile int 后，两个线程分别执行 1000 次 count++，最后必然是 2000 吗？

正确。可能丢失更新。需要 AtomicInteger、synchronized 等保证整体递增正确。

JMM 是 Java 内存模型，它不是具体的物理内存布局，而是约束线程之间如何读写共享变量的规范。happens-before 可以理解为 JMM 对操作之间建立的有序性和可见性保证。比如同一线程的程序顺序、对同一个 volatile 变量的写与后续读、同一把锁的解锁与后续加锁，以及这些关系的传递性。用 volatile ready 发布状态时，写线程在 ready=true 之前写入的 data，能够在读线程观察到 ready=true 后被正确读取。但 volatile 不保证 count++ 这种复合操作的原子性，要用 AtomicInteger 或 synchronized 等方式处理。

你现在应该能解释这 5 句话

  1. JMM 是规范，不是 CPU 缓存结构图。
  2. 线程 A 先执行，不代表 B 就一定能看到结果。
  3. happens-before 是顺序与可见性的规则，不是时间戳的大小关系。
  4. volatile 写 / 读可以把此前的普通变量写入“发布”出去。
  5. volatile 解决不了 count++ 的原子性问题。
